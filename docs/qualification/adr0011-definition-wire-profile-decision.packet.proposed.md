# ADR0011 definition wire/profile decision packet (proposed)

**Status:** proposal for maintainer adjudication only. **Authority:** 0. No policy, schema, profile, source pin, installed provider, or production path is changed or approved by this document. This packet does not acquire a definition or attest to a live provider.

## Evidence and boundary

- `internal/lspwire/read_frame.go:15-20,22-44,72-95,98-113`: `FrameBytes` counts bytes consumed for a *complete valid frame*, not `bufio` prefetch; observation contains a hash, not raw bytes. `ReadWithFrameIfWithin` can decode an over-capture-cap frame and return an observation but no raw copy. A failed/partial read returns no complete-frame observation (`:84-87,105-112`). Its cap bounds raw retention, **not reader allocation or wire work** (`:72-76`).
- `sessionruntime/sessionruntime.go:250-255,824-845,880-921`: definition raw-frame capture is private, opt-in, and separately caller-capped. The runtime reads *each* encountered frame with observation/capture; `result.Bytes` is accumulated re-marshaled decoded-message bytes checked against `maxBytes` (`:880-885`). Only after the response ID is matched and accepted does it record `ResponseReadObservation`; only a retained successful matched response supplies definition raw bytes (`:891-921`). The current observed `FrameBytes` is **not enforced as a wire ceiling** on each message. An unmatched notification or response can consume wire bytes independently of the matched result.
- `sessionruntime/method_frame_correspondence.go:18-27,28-48,63-82`: `2 << 20` (2,097,152) is a **private replay/correspondence work ceiling**, not admission, retention, or a selected provider wire policy. The caller-selected capture cap is separate; correspondence requires captured raw response, matching observation, decoded result and ID. Do not convert this numerical coincidence into existing wire enforcement.
- `sessionruntime/sessionruntime.go:1658-1690`: initialize captures reported `serverInfo.name/version`, position encoding and `definitionProvider` support. Reported server information and advertised capability are assertions by the server, not executable authentication.
- `internal/managedprocess/identity.go:30-42,67-76,100-142`: managed identity distinguishes path locator, executable-byte digest and count/status, arguments/config/environment and workspace. Opened-file measurement and path comparison can fail or race. A digest is bounded local evidence about measured executable bytes, not proof of the responding process's build or provider behavior.
- `docs/qualification/policies/adr0011-definition-exact.proposed.json:12-16` currently leaves `framedWireCapBytes` null and calls the framed cap an unavailable implementation prerequisite; its decoded-body cap is 1,048,576 and result limit is 524,288. This is a proposed policy artifact, not an adopted wire gate.

## Wire decision (not yet made)

**Recommended safe boundary for review:** propose an inclusive **2,097,152-byte ceiling for each complete inbound LSP frame** (headers and body as actually consumed, not `Content-Length` body alone), throughout the definition transaction, including notifications, unrelated responses, error responses and the matched response. At exactly 2,097,152, a complete valid frame passes the proposed wire comparison; at 2,097,153 it fails. An alternative *matched-success-response-only* ceiling leaves preceding/interleaved frames unbounded by this new rule and must be an explicit different decision, not a reinterpretation of the recommended choice. A complete-frame admission decision still requires separate finite message/deadline and allocation bounds; it does not make incomplete reads bounded.

**Precedence proposal:** (1) wire: independently compare each *observed complete frame* against the inclusive frame ceiling before treating that frame as eligible; (2) decoded: separately enforce the manager's decoded-message/body accounting ceiling of 1,048,576 (confirm exact variable/contract before adopting), without substituting it for frame bytes; (3) result: enforce the definition result's 524,288-byte limit against the designated raw result representation, independently of both earlier gates; (4) transaction accounting: message count, cumulative decoded bytes, deadlines and work remain distinct. If several bounds fail, retain the earliest causally observed terminal reason and do not reinterpret wire excess as decoded/result excess. Specify terminal taxonomy and attribution at adoption; current `result.Bytes` is re-marshaled decoded messages, not exact wire bytes. An otherwise acceptable result does not erase an earlier over-ceiling frame.

**Synthetic RED design (future work, not executed here):** construct valid LSP frames whose *actual consumed header plus body* totals exactly 2,097,152 and 2,097,153 respectively, while JSON decoded-body bytes stay **strictly below 1,048,576** and raw `result` bytes stay **strictly below 524,288**; use syntactically valid insignificant JSON whitespace in the framed body to isolate wire comparison from the re-marshaled decoded-message accounting and result checks; keep the header within its unchanged independent limit and ensure the reader's framed-body limit admits both fixtures. Assert inclusive success/failure at the wire boundary on (a) matched success and (b) a preceding unrelated valid frame followed by a small matched success. Assert the over case fails for wire excess, not capture omission, header parsing, decoded cap, result cap, message count, or timeout. If the existing framed-body limit rejects either fixture before frame completion, that is a **test-design prerequisite** requiring a test-only reader limit, not permission to raise production limits. Count the decoded-message size by the runtime's re-marshaling rule, not by the whitespace-padded framed body length. A second fixture can show an over-capture-cap but within-wire-limit frame remains observable without raw retention. Failure on a partial header/body, EOF, timeout, or claimed `Content-Length` without complete bytes cannot establish exact complete-frame size; a partial-frame byte/work guard requires its own instrumentation and decision.

## Provider identity decision (choose exactly one)

All options require a maintainer to state the executable/build, accepted version and capability expectation, exact profile pin and definition of sufficient measurement. None is inferred from the installed `gopls` name or from server-reported metadata alone.

1. **A — Reported identity only:** admit by `serverInfo.name/version` plus `definitionProvider` and profile label. Weakest; spoofable or mutable server assertions, no executable-byte binding. Not recommended for an irreversible identity commitment.
2. **B — Measured local executable plus reported metadata (recommended conditional target):** bind an exact bounded opened-executable byte digest/length/status and launch configuration/profile pin to the same managed generation, then require specified reported name/version and `definitionProvider`. Fail closed on unavailable/raced measurement or mismatch. This is stronger local correspondence, **not** proof of build provenance, source equivalence, response authorship or production authority. Do not populate a pin until the maintainer approves the exact candidate and measurement procedure.
3. **C — Independent build-provenance attestation plus B:** require separately verified build provenance linking the measured executable to a named source/build and its trust root, in addition to B. Strongest claim but needs an actual independently reviewable attestation and verifier; absent that evidence, remain unqualified rather than silently falling back to B.

Options are mutually exclusive admission-strength decisions for this packet; the maintainer may reject all three or request a revised packet. A provisional investigation can collect bounded facts without selecting any option or changing a pin.
