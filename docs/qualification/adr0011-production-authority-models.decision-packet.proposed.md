Each model must specify the original-byte canonicalization, domain separators, byte bounds and role URIs *without changing accepted predecessor IDs or bytes*. A digest proves integrity only relative to an independently chosen expected digest; an entire rehashed claimant graph is not its own oracle. The immutable host selection need not become a 22nd immediate final ref. Final still carries exactly 21 immediate refs, with three separate ancillary ledger/accounting refs and a distinct attempt manifest; `accounting_digest` hashes complete canonical accounting bytes. Selection, replay and external publication proof are separate gates.

## Four concrete authority models

### H — host-configured immutable authority

- **Principal / boundary / selecting versus consuming:** An identified local host operator, through a privileged provisioning step outside request/MCP input, approves and installs an exact versioned selection bundle for all five identities. A concrete acquisition owner consumes a pinned bundle; requesters, providers, ledgers and replay claimants may only supply candidates. A protected path or `0700` root is a custody condition, not operator authentication against the same UID.
- **Provisioning, rotation, bytes:** Provision a canonical closed bundle containing original bytes or exact selectors/digests/lengths plus a verifiable original for plan, executable measurement policy, and each policy. Operator approves version `v`, not an ambient `latest`; rotate by installing `v+1` for *new* attempts, retaining `v` and its exact original bytes for old attempts. Define a version-to-expected-digest root outside mutable claimant storage.
- **Startup/restart and cross-process:** Start disabled until the configured version, root descriptor and every original are verified. Freeze one selected version per attempt; restart reopens and compares that version and original bytes, never refreshes from current defaults. Two processes must agree on the same version/attempt selection through a separately proven shared lock/fence or single authorized selector service; the current process-local mutex does not supply this. A crash after install but before readback is uncertain, not a fresh selection.
- **Substitution / rollback / local assumption:** Reject coherent claimant rehashing against operator-held expected bytes, cross-process version disagreement and stale-revision substitution. To resist rollback of *the operator bundle itself*, require an independently retained monotone authorized-version anchor or an explicit signed approval chain; ordinary mutable host config supplies neither. Same-UID modification remains outside the claimed adversarial guarantee unless an actual stronger boundary is specified.
- **Failure, default-off, replay, migration:** Missing, changed, ambiguous, unreadable, postcommit-unverified or revoked version means no invocation/final; `NewDisabled` stays the only production constructor until separately approved. Qualification must demonstrate pre-WRITE freeze, fresh readback, restart and competing-process substitution/replay. Migrating host config requires retaining old versions and a reviewed mapping for old attempts; revocation of new use versus historical replay is a separate lifecycle decision.
- **Irreversible approvals:** Naming the operator and trusted provisioning channel, root/version anti-rollback rule, exact implementation measurement subject, and whether old version use/replay survives revocation.

### R — repository-pinned manifest with host verification

- **Principal / boundary / selecting versus consuming:** Maintainers review a canonical, versioned manifest in the repository that enumerates candidate plan/schema/policy/implementation objects. A *separate host operator* pins the **exact manifest bytes/digest** and checks originals; the repository is a distribution source, not an authenticated selector. If the host simply accepts `HEAD`, this model has no independent authority and must be rejected.
- **Provisioning, rotation, bytes:** The manifest binds complete content-addressed objects, role URIs, lengths, allowed execution measurements and a version. A host installation independently approves the manifest digest and freezes the attempt-specific query/nonce/selection before invocation. Repository update alone does not rotate active authority; host must explicitly approve a new pinned digest. A Git commit, clean tree and signed-looking file do not prove the running binary corresponds to `implementation_digest`.
- **Startup/restart and cross-process:** Every process verifies the same host-pinned manifest digest and exact original bytes; absent pin or partial manifest is fail-closed. Restart replays its attempt-bound old digest rather than re-resolving a branch/tag. Processes require common durable pin visibility/fencing or single selector authority; no current cross-process lease is assumed.
- **Substitution / rollback / local assumption:** Host comparison detects candidate-byte substitution and unauthorized HEAD movement, but malicious or rolled-back *host pin* remains possible without an independent monotone anchor. Same-UID access to repo and host config is not a separation-of-principals claim. Repository-pinned alone is insufficient; with a substantive independent host pin it overlaps the Hybrid model below.
- **Failure, default-off, replay, migration:** Unknown commit/manifest, unavailable original, disagreed or revoked host pin, implementation mismatch and verification uncertainty cause no invocation. Preserve `NewDisabled`; row qualification must test branch rollback, manifest rehash with an unchanged host pin, binary mismatch and restart replay of old originals. Migration needs pin/version mapping, old manifests and original bytes. Revocation cannot silently delete old replay evidence.
- **Irreversible approvals:** Which repository authority may propose changes, whether manifest is a plan source or plan selector, exact host pin provenance, repository revision semantics and anti-rollback policy.

### O — separately provisioned owner authority

- **Principal / boundary / selecting versus consuming:** An administratively separate owner service or offline provisioning principal is the sole selector of a signed/otherwise authenticated versioned identity bundle and attempt grant; the local acquisition process consumes and verifies it. This is **an option, not an existing service**. Authentication, key custody and the trust root would need explicit approval; network transport or same UID is not a proof.
- **Provisioning, rotation, bytes:** Owner issues a closed grant binding the five originals/identities, permitted query/workspace/session/generation and one attempt/nonce, with canonical bytes and expiry/revocation semantics. Rotate the signing/provisioning authority and grants under a retained versioned trust-root transition, with old verification material preserved if historical replay is required. No secret or signature format is chosen here.
- **Startup/restart and cross-process:** Start disabled until authenticated authority/grant and every original are verified. Restart consumes exactly the saved attempt grant, never requests a fresh replacement for an in-flight attempt; another process verifies the same grant and must prevent duplicate use by a proved shared attempt claim/fence. Offline outage may use only a previously authorized immutable snapshot **if separately approved**; otherwise fail closed.
- **Substitution / rollback / local assumption:** Authentication can separate a compromised repository/local claimant from the selector *if* private credentials and monotone revocation/version state are actually independently protected. A local same-UID process that can steal verification keys or alter an offline snapshot invalidates that guarantee. Signed old grants still need anti-replay/rollback policy.
- **Failure, default-off, replay, migration:** Unknown signer, unverified grant, unavailable service, stale/reused nonce, revoked version or uncertain readback block new attempts. `NewDisabled` remains. Qualification needs authenticated original and grant replay, duplicate/restart/competing-process tests and negative issuer-substitution tests. Migration/revocation must account for key rotation, old grant verification, and availability costs; physical erasure is not implied.
- **Irreversible approvals:** Whether authority is independent at all, who operates it, credential/trust-root and grant semantics, outage policy, nonce reservation, key rotation and revoked historical replay.

### Hybrid — host approval of repository-distributed candidates (**conditional recommendation**)

- **Principal / boundary / selecting versus consuming:** The repository proposes reviewed, immutable candidate bytes. An identified host operator separately authorizes **one exact manifest digest plus implementation measurement and policy set**, and the host owner freezes a query-specific selection original before invocation; acquisition/replay consumes that frozen original. Repo revision or claimant-supplied manifest cannot silently change the approved tuple.
- **Provisioning, rotation, bytes:** Candidate manifest lists exact canonical plan-template, schema, policy and implementation-measurement inputs; host provisioning pins its whole-file digest/version and independently retains verified original bytes. Per-attempt host selection binds approved tuple to READY session/generation, prepared source, Git BEFORE ref, query, collision-safe nonce, expected custody bytes/ref. `plan_id` is derived from an independently selected exact plan original, **not** guessed from the query; actual request key is later observed from manager WRITE. Rotating any candidate requires a new manifest **and** explicit host approval/version, not an implicit repo deployment.
- **Startup/restart and cross-process:** Fail closed unless host pin, exact candidate originals, approved measurement, private root and per-attempt selection all verify. Restart recovers the exact version/selection/attempt record; no `latest` fallback. Cross-process selection and cutover require a separately qualified shared fence/authority or serialization through a single host selector; current `targetLock` and Lane C REVISE do not supply it.
- **Substitution / rollback / local assumption:** Unchanged host pin rejects a coherent repo/claimant rehash; independent held attempt tuple rejects a rehashed closure. To reject rollback of both repo and host pin, the host needs a durable monotone authorization version or separately approved approval history. Same-UID hostile replacement remains unproven; this is local custody under a trusted operator, not producer authentication.
- **Failure, default-off, replay, migration:** Host/repo disagreement, absent plan original, mismatched executable bytes, uncertain publication, competing selection or revocation ambiguity means no invocation or issuance. Keep `NewDisabled` and `PublishReferences` fail-closed. Qualification must independently replay selected original bytes and timing, exact no-replace/readback, changed-repo/unchanged-pin, changed-host/old-attempt, restart and two-process negatives. Migration requires retention of old manifests, approvals and attempt tuples; explicit revocation semantics distinguish future selection from old replay.
- **Irreversible approvals:** The host principal and pin channel, manifest role/plan namespace, executable measurement scope, per-attempt version/nonce allocator, rollback anchor and revocation policy. None is chosen here.

## Comparison and proposed decision

| Criterion | H: host config | R: repo + host verification | O: separate owner | Hybrid: repo candidate + host approval |
|---|---|---|---|---|
| Independent expected original | Host bundle, if genuinely selected | Host-pinned digest and verified repo originals | Authenticated owner grant | Host-approved pin and attempt tuple |
| Change control | Host operator only | Repository proposal **plus** host pin | External authority | Repository proposal **and** host approval |
| Same-UID hostile substitution | Not solved by private root | Not solved by Git or host pin alone | Only if credentials/trust root separately protected | Not solved without stronger host boundary |
| Offline availability | High if pinned files survive | High if host pin and repo originals survive | Variable; immutable offline grant only by approval | High if approved pin and originals survive |
| Cross-process / rollback proof currently implemented | No / no | No / no | No / no | No / no |
| Operational migration/revocation burden | Versioned local bundles | Dual repo+host version inventory | Grant/key lifecycle | Dual approval plus attempt-tuple inventory |

**Recommend Hybrid for maintainer consideration, conditionally, not as a decision.** It separates reviewable candidate distribution from the host's actual selection, works in a local default-off deployment without assuming an external authority service, and gives an independent digest against repository/claimant substitution. Its advantages vanish if the host pin is `HEAD`, if the actual executing implementation is not measured, if a second process can silently select a different version, or if rollback/revocation has no independent rule. H is a simpler candidate if the host bundle is itself protected and versioned; O is the stronger administrative separation only if an actual owner service and credentials are warranted. R alone has no trustworthy selection without the host pin and then becomes a limited Hybrid.
