# Security and trust boundaries

`lsp-trace` starts a caller-selected language server with the invoking user's permissions. A server may execute project build or restore logic, read workspace files, access the network, and emit secrets through stderr or opaque `CallHierarchyItem.data`. Use only trusted server binaries and workspaces; sandboxing is the deployer's responsibility.

The client passes arguments directly without a shell, performs no automatic network access, and does not invoke Git or repository hooks. V3 records command arguments and explicit `--server-env` names, but embeds neither environment values nor the working-directory path. It records domain-separated SHA-256 identities for the effective inherited-plus-override environment and cwd, plus the effective variable count and explicit redaction state. The cwd identity uses a cleaned absolute process path but does not resolve symlink aliases; lexical aliases of the same directory can therefore produce different digests. These are tool-derived identity claims, not independently authenticated facts; hashes of low-entropy or guessable values can enable confirmation attacks. Explicit server arguments and environment names may themselves be sensitive.

`--trace-lsp PATH` writes an opt-in JSON Lines protocol transcript with deterministic sequence numbers and directions. Transcripts contain raw sent and received JSON-RPC payloads and may expose source text, paths, identifiers, opaque `CallHierarchyItem.data`, or secrets; protect and redact them before sharing. The CLI does not include environment values in the transcript. Graph output and captured server stderr may also be sensitive. Output and transcript files are created with mode `0600`; stdout remains subject to the caller's redirection and logging environment. Review retained qualification evidence before sharing it.

Authority remains field-specific: invocation/provenance claims are caller-supplied, graph and discovery observations are server-reported, normalized identities and metadata are tool-derived, and receipts establish only bounded integrity/custody. None of these authorities authenticate the others.

V3 sensitivity policy covers invocation arguments, explicit environment names, workspace/source/output paths, opaque node data, diagnostics, captured server stderr, and trace transcripts. `automatic_redaction` is false: environment values and the cwd path are omitted by specific projection rules, but covered content is not generally scrubbed. Bundle custodians are responsible for access control, retention, and any redaction before sharing. On POSIX, selector and generation-file mode `0600` plus generation-directory mode `0700` protect those local objects only; the selector basename and directory entries may remain visible to principals able to list the destination, and stdout, backups, copied files, target paths, error text, and digests require separate controls. Publication-failure records are private strict JSON and are reported as retained only after their file sync and the platform's directory-durability step, but they still disclose target path, error text, and an exact-byte digest. Custody and failure receipts expose `directory_durability`: `CHECKED` means directory sync completed, while `UNAVAILABLE_ON_PLATFORM` means the runtime provides no supported directory-sync operation (currently Windows). The unavailable state is an explicit durability limitation, not proof of directory-entry persistence; file sync, semantic validation, and transactional selector publication remain required, and ordinary directory open/sync errors still fail publication. Receipts provide integrity/custody checking, not authenticity, signatures, producer identity, source truth, or independent confirmation of hidden process inputs.

Report vulnerabilities privately to the repository maintainers rather than publishing exploit details in an issue.
