## Complete capability exchange

`CAPABILITY_EVENTS.initialize` is a client→server `initialize` request and server→client response; `initialized_notification` retains the exact complete client→server `initialized` notification frame, ordinal and direction, with strict raw JSON-RPC 2.0 shape (`method: initialized`, no `id`, `params: {}`); `events[]` are server→client register/unregister requests and client→server responses. Each exchange retains complete request frame bytes, exact request ID/method/parsed params and frame ordinal; complete response frame bytes or an explicit pending null, response ID/ordinal/direction, success/error/pending status, result/error, and target WRITE ordinal. The REQUEST_WRITE role separately binds `completed_frame_ordinal`; replay must compare it with the CAPABILITY_EVENTS target WRITE ordinal against verifier-held WRITE custody. `CAPABILITY_EVENTS.observed_frames` separately retains up to 16,387 complete ordered request/response/initialized-notification frames, including unmatched or duplicate responses and notifications, so replay must compare the complete set with the independently held capability stream, reject omissions/duplicates/extra frames, and bind each exchange to its exact frame occurrences. This bounded stream is representational; JSON Schema does not establish completeness. Parsed mirrors and frame descriptors are **claims**, not independently established correspondence; replay must strictly parse both complete frames, reject decoded duplicate keys, bind request/response IDs and opposite directions, and compare all bytes and ordinals with verifier-held originals. JSON Schema alone cannot assert cross-field ID equality, verify raw frame contents, or establish that a result belongs to its stated status.

**No `effective_ordinal` field exists.** Initialization completes only on the strict order client initialize request < successful matching server response < exact client initialized notification < target completed WRITE. A target WRITE before completion, a missing, duplicate, malformed or prematurely ordered notification, an initialize error or pending response, and any register/unregister request or successful response before completion are `INVALID_CHRONOLOGY`, never applicability `UNKNOWN`; no static support overrides this. A successful capability exchange is effective only when initialized notification ordinal < request ordinal < successful matching response ordinal < target completed WRITE ordinal. Successful registration activates each exact `(registration ID, method)` only then; a failed or pending registration does not. Successful unregister removes only the active exact pair; an error leaves it active. Pending at WRITE is UNKNOWN only when no prior verified support decides the selected target: an unacknowledged matching registration is inactive but leaves support unresolved without another proven source. A pending unregister leaves its already active registration in force until a successful matching acknowledgement; it is SUPPORTED at an earlier WRITE if that active selector matches, and removal applies only at a later WRITE after success. Both V4 method originals state these two rules explicitly. Late success never applies retroactively. Duplicate/mismatched/reversed response is INVALID_CHRONOLOGY, not support. The additional complete initialized notification counts toward the mandatory transaction quota and the 16,387-frame V4 maximum; over-cap stops, it does not drop a frame. The schema's pending/success/error shape checks cannot alone classify these temporal facts.

## QUERY_APPLICABILITY and graph

The 13th role `QUERY_APPLICABILITY` has exactly one QUERY and one query SOURCE predecessor and binds transaction/workspace/session/generation, selected QUERY and SOURCE selectors, exact URI bytes, explicit language presence and bytes, ordinary or notebook-cell kind, and conditional enclosing notebook type/URI/source selector. A replay verifier must derive expected values independently from held QUERY/SOURCE/workspace/notebook originals, compare full bytes and null/presence semantics, and reject cross-transaction or claimant-only values. The schema cannot establish that equality. `REQUEST_WRITE` additionally requires QUERY_APPLICABILITY; `TERMINAL` has nine fixed required non-SOURCE predecessors plus 1–256 selected SOURCEs, excluding optional PROCESS; `READBACK` has ten selected fixed non-SOURCE predecessors including TERMINAL plus selected SOURCEs and optional PROCESS. TARGET_EVENTS is capped at 256 (one RESULT_READ plus at most 255 target SOURCEs), TERMINAL at 265, READBACK at 267, complete transaction at 268. Every fixed role has a role-specific exact count; aggregate caps confer no extra role entitlement.

Nonmatching and unrelated pending entries remain UNSUPPORTED where no other support exists; independently established static support remains SUPPORTED. The oracle now folds initialize in response-ordinal order and rejects a registration response preceding initialize success. `response_mirrors_test.go` checks raw response `method`, different ID, number/string ID mismatch, and boolean-versus-number ID for both methods. A later review found the Python offline `validate_exchange` accepted a boolean response ID for numeric request ID (Python `True == 1`) and failed to reject a response carrying `method`; both are now explicit rejected-input fixtures with an observed RED and GREEN. The Python validator now checks exact ID type and value, method-free response, JSON-RPC shape, and method-appropriate success result. A subsequent review identified that `error:null` was treated as an unsuccessful response instead of an invalid frame. Both Python and Go now reject null, boolean-code and missing-message error objects; Python additionally rejects parsed-error mirror mismatch. Both changes have named RED/GREEN observations. Another read-only review found Python `json.loads` accepted non-JSON `NaN` constants in otherwise matching raw-frame streams; matched-stream malformed request and response fixtures produced an assertion-specific RED, and `strict_frame` now rejects non-JSON constants with a named GREEN. A subsequent review proposed marking pending unregister UNKNOWN even with a previously active matching registration; parent comparison against response-gated effectiveness and the no-retroactivity rule rejected that proposed state change and added both-method earlier/later WRITE fixtures. The V4 method-policy pending language was clarified, so all 54 candidate selectors were recomputed under the new V4 policy digests; historical V2/V3 originals and vectors remain unchanged. Independent read-only review then found an ORDERED_OR oracle bug: a later UNKNOWN pattern filter erased an earlier proven language match. Both filter orders for both methods produced the named RED/GREEN; separate active matching and UNKNOWN registrations also received both-method RED/GREEN, with a proven match taking precedence. These are test-only state-oracle corrections, not selector issuance or B4 replay. It is not B4, an issuer, or proof of host-owned completeness. A separate exact-byte and semantic review must challenge the corrected schema, raw-frame/parsed-field correspondence and this oracle before `ACCEPT_GENERIC_LSP_CAPABILITY_EXCHANGE_V4_FOR_IMPLEMENTATION_ONLY`; the target is **not issued**, and B4, issuance, request/admission authority, qualification, and public wiring remain paused.
