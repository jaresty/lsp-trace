# ADR0011 references selected-limit allocation correction — proposed

**Decision requested:** `ACCEPT_REFERENCES_LIMIT_ALLOCATION_FOR_IMPLEMENTATION_ONLY | REVISE | REJECT`. This is a prospective allocation correction to frozen private synthetic checkpoint `e66d5a7b` and the reachability packet at `be49cffe`; it neither changes accepted numerical ceilings nor qualifies an occurrence. No source, accepted contract/matrix, public selector or raw-retention default may be changed on the strength of this proposal alone. Source/manifest bytes must be re-pinned and re-reviewed after any implementation.

## Distinct accounting points and owner selection

1. For each of the two default-off managed `documentSymbol` and `references` transactions, Owner selects `MaxMessages=4` and `MaxBytes=4,194,304` decoded **response-body aggregate** (sum of `encoding/json`-marshaled read messages at `sessionruntime/sessionruntime.go` before accepting a fifth or over-budget body). A fifth read is rejected regardless of total bytes. `MaxBytes` is *not* a framed-request or result-token cap. A total exactly at the cap is eligible only if every independently selected lower cap and custody check passes. Introduce a private, positive `RoundTripRequest.ADR0011PrivateLimitAllocationV1` marker (`json:"-"`, default false) set only by the host-private ADR0011 Owner for its exact `documentSymbol` and `references` requests; it is a **behavior opt-in, not proof of Owner provenance or producer authentication**. In **both** `eligibleOwnedMethodRequest` and `buildOwnedMethodPair`, permit `MaxBytes` up to 4,194,304 only when that marker is true, method is one of those two, `CaptureOwnedMethodPair` is true, `ExpectedOwnedDocument` is present and matched, and positive `MaxMessages≤4` plus independent 65,536-byte params bound hold. The marker must not be inferred from method, `CaptureOwnedMethodPair`, frame caps, or `MaxBytes` alone; a caller merely setting an existing opt-in or a larger `MaxBytes` retains the historical 1 MiB eligibility ceiling. Marker absent—including opted-in historical definition/references/documentSymbol callers—preserves exact behavior; unsupported methods and definition do not acquire the new allocation even if marked. The Manager's prior historical limits for ordinary operations remain unchanged. Add paired tests holding every other request field constant with marker absent/present across 1 MiB and 4 MiB boundaries and verify absent never returns an owned pair. This marker alone never admits an occurrence or enables public issuance. Require `r.RequestBytes`, per-response `len(raw)`, `r.Bytes`, and `r.Messages` to stay consistent with the selected positive limits; no aggregate-only proof admits an oversized result.
2. Owner independently selects **2,097,152 bytes per exact staged request frame and per exact staged response frame**, counted including the Content-Length header, for each method; both captures remain private, optional and all-or-nothing. The existing `maxMethodFrameCorrespondenceBytes=2<<20` independently bounds reconstructed request and retained response verification; request and response tests may not be interchanged. Above-cap frames are never retained as complete evidence or accepted by the private final; a completed response body alone cannot stand in for the request frame. The existing Manager 1 MiB capture selection is not the selected 2 MiB allocation.
3. Owner independently selects a positive **4,194,304-byte exact framed-request write guard** before an eligible completed write. Count canonical header **and** marshaled JSON-RPC body (`len("Content-Length: "+decimal(bodyLen)+"\r\n\r\n")+bodyLen`), using the same request ID, params copy and encoder semantics as `lspwire.Writer`. No overflow, inferred header width, double-encoded substitute or after-write-only rejection. Add a private Manager opt-in counting seam, verify the subsequently observed completed `RequestWriteObservation.FrameBytes` and digest against the original frame if capture is selected, and return a typed redacted resource failure without a completed write on over-limit. Do not raise or alter omitted-mode `lspwire.DefaultLimits`; do not conflate this guard with `m.wire.MaxBodyBytes`, which counts only the body. The Owner-built fixed compact params may make this 4 MiB edge unreachable at Owner: its owning lower-level seam must still have exact at/over witnesses, with Owner reachability reported honestly.
4. Retain independent **65,536-byte exact raw `params` token**, **1,048,576-byte exact raw `result` token/payload** for both method outputs, **1,500,000-byte complete canonical record** (including LF where that role requires it), and **1,048,576 scanner byte visits**. Enforce raw spans against original retained write/read bodies and before private payload publication/evaluation. A 2 MiB frame or 4 MiB aggregate does not authorize a >1 MiB result. A >1 MiB scanner input is rejected by a length precheck before any +1 visit; report that distinctly. Keep the per-run/root raw, uncertainty, diagnostic, work, 1,000-element and timeout budgets independent and default-off. Do not silently replace the accepted `16 queries/17th rejection` matrix case with sixteen separate single-query Owner calls; an acquisition-batch boundary is still missing.

## Required bounded falsifiers before any qualification claim

- At/over tests at each **owning seam**, varying only one bound, including framed write 4 MiB/+1 pre-write, staged request and response frame 2 MiB/+1 separately, Manager decoded aggregate 4 MiB/+1 and four/five messages separately, exact params and result 65,536/+1 and 1,048,576/+1, complete canonical record 1,500,000/+1, scanner exact 1,048,576 visits and +1-byte precheck. Assert typed redacted failure, no partial/cross-key completed frame, no new issued receipt; separately verify uncertain postcommit publication remains quarantined.
- For Owner-end-to-end tests, declare every shadow or unreachable fixture `SHADOWED` or `UNREACHABLE_AT_THIS_LAYER`, never `PASS`. Owner fixed params make 4 MiB framed request and 2 MiB request-frame edges unreachable; the 1 MiB result plus strict envelope may prevent a 2 MiB eligible response-frame edge. To reach a 4 MiB decoded response aggregate, use independently bounded unmatched notifications plus a valid final keyed response, under a positive deadline, with strict matching and one request key; distinguish the owned-pair raw-result cap. If the wire reader itself has a narrower body bound, disclose and test that obstruction rather than widening it silently.
- Keep pre-change omitted-family process bytes pinned at 43,541 bytes / SHA-256 `d9630f80e4b8df33f345c8dfb52659b9813adeca5f884935d6dae680e39e95c5`; explicit `CALLS_ONLY` is not implemented and `relations:["CALLS"]` is not an equivalent parity assertion. Three historical legacy success-arm tests remain RED until independent production query admission, not because synthetic limit tests may route around `PublishReferences`.

Does Manager/owned-pair accounting leave each selected result, staging and aggregate guard independently falsifiable? Are the unreachable at/over cases classified honestly? Any answer requiring a different bound or silent public enablement is `REVISE`, not implementation acceptance.
