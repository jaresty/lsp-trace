# ADR 0003: Add an optional MCP server with persistent language-server sessions

- **Status:** Superseded by [ADR 0003: Activate always-local Stage 2 lifecycle tools](0003-always-local-stage2.md)
- **Date:** 2026-09-02
- **Historical scope:** This document preserves the former staged six-tool, containment-gated design as provenance only. It is not current runtime or acceptance authority.
- **Decision owners:** LSP Trace maintainers
- **Scope:** Optional MCP transport, offline evidence operations, and reusable live LSP sessions
- **Related commands:** `incoming`, `slice`, `inspect`, `filter`, `verify`, `schema get`, `validate`

## Context

The `lsp-trace` CLI starts one language-server process for each live traversal. Some servers spend substantial time restoring dependencies, indexing a workspace, and warming caches before Call Hierarchy requests become useful. Repeating that lifecycle for every `incoming` or `slice` invocation is expensive and can make iterative investigation impractical.

An MCP server is itself a persistent process. It can expose LSP Trace operations to agent clients while retaining initialized language-server sessions across requests. Persistence is useful only if session reuse remains explicit, isolated, bounded, and represented honestly in evidence.

MCP transport does not authenticate source code, language-server output, the producer, execution context, or retained artifacts. A long-lived server also does not provide a repository-wide snapshot: the workspace may change between requests, servers differ in file-watching behavior, and only directly observed content identities can be asserted.

## Decision

Add an optional stdio MCP server as a separate binary:

```text
cmd/lsp-trace-mcp
```

The CLI remains supported and authoritative for its existing command contracts. The MCP server is an adapter over shared internal operations, not a replacement CLI and not a shell wrapper around the `lsp-trace` executable.

The intended MCP v1 surface includes both offline operations and the LSP-dependent `incoming` and `slice` operations. Delivery is staged as implementation and acceptance sequencing, not as a decision to omit live tracing from the completed v1 capability. Stage 1 is implemented and accepted by this ADR; Stages 2 and 3 remain unimplemented and gated:

1. expose offline, read-only evidence operations;
2. add explicit lifecycle inspection and control;
3. enable live `incoming` and `slice` traversal backed by persistent LSP sessions after the lifecycle and evidence contracts pass their acceptance gates.

The MCP process starts in offline-only mode unless launched with an explicit `--enable-live-lsp` capability flag. `lsp_trace_v1_capabilities` is always advertised. Every canonical tool and reserved later-stage entry reports one exact `availability` value from the closed enum `NOT_IMPLEMENTED`, `CONTAINMENT_UNAVAILABLE`, `RUNTIME_DISABLED`, or `ENABLED`: `NOT_IMPLEMENTED` means no handler from that stage was compiled and accepted into this binary; `CONTAINMENT_UNAVAILABLE` means a persistent lifecycle/live handler is implemented but the closed process-lifetime containment result is `UNAVAILABLE(reason, failed_check)` because a required check was unsupported, indeterminate, failed, mutable, or incomplete; `RUNTIME_DISABLED` means an implemented, containment-capable handler is disabled by process-start policy; and `ENABLED` means implemented, containment-capable, and runtime-enabled. Offline tools never use `CONTAINMENT_UNAVAILABLE`. `tools/list` advertises exactly canonical entries whose availability is `ENABLED`; aliases are never advertised. Availability is resolved in this precedence: implementation absence selects `NOT_IMPLEMENTED`; otherwise persistent lifecycle/live containment failure selects `CONTAINMENT_UNAVAILABLE`; otherwise a false runtime gate selects `RUNTIME_DISABLED`; otherwise `ENABLED`. `--enable-live-lsp` therefore changes only containment-capable implemented lifecycle/live entries between `RUNTIME_DISABLED` and `ENABLED`; it cannot override `NOT_IMPLEMENTED` or `CONTAINMENT_UNAVAILABLE`. In Stage 1 every lifecycle and live entry remains reserved with `NOT_IMPLEMENTED` regardless of the flag. The containment probe occurs during process startup, before capability publication or any language-server execution, and produces exactly `VERIFIED` or `UNAVAILABLE(reason, failed_check)`; the manager consumes this internal, bounded, non-authoritative result without exposing sensitive credentials or paths. The result, runtime flag, and complete availability projection are fixed for the process lifetime and require a new process to change; exact OS enumeration, evidence, and mechanics remain Stage 2-owned. When enabled, live traversal requests require an explicit named profile and workspace. Lifecycle `status`, `stop`, and `restart` use only the exact selector contract below, and `list` uses only its defined list input; neither input family accepts or requires traversal workspace/profile fields. No MCP operation automatically selects a language server or named profile.

Stage 1 is an independently shippable runtime and contract: its binary, advertised offline tools, schemas, transcripts, and manifest entries neither depend on nor imply Stage 2 or Stage 3. The planned full v1 feature set is not complete until the accepted lifecycle and live traversal tools are available behind the capability gate.

## Stage 1: offline evidence operations (implemented)

Expose these initial MCP tools:

```text
lsp_trace_v1_inspect
lsp_trace_v1_filter
lsp_trace_v1_validate
lsp_trace_v1_verify
lsp_trace_v1_schema_get
lsp_trace_v1_capabilities
```

These six canonical tools start no language server. They reuse the same structural, semantic, accounting, custody, authority, and claim-ceiling logic as the CLI.

The exact v1 naming rule is: every public tool has one canonical versioned name; offline and live names match `lsp_trace_v1_<operation>`, and lifecycle names match `lsp_session_v1_<operation>`. `tools/list` advertises and counts canonical names only. The twelve existing unversioned names (`lsp_trace_inspect`, `lsp_trace_filter`, `lsp_trace_validate`, `lsp_trace_verify`, `lsp_trace_schema_get`, `lsp_trace_capabilities`, `lsp_session_list`, `lsp_session_status`, `lsp_session_restart`, `lsp_session_stop`, `lsp_trace_incoming`, and `lsp_trace_slice`) remain callable v1 compatibility aliases, but aliases are never advertised or counted. Dispatch canonicalizes a recognized alias to its exact canonical v1 name before reserved-name lookup, input-schema validation, capability gating, handler selection, manifest/envelope-variant lookup, and envelope construction; therefore canonical names and aliases have identical validation-before-gate precedence, disabled behavior, schemas, results, errors, gates, and compatibility obligations, and envelope `tool` is the canonical versioned name. An unsupported versioned name is an unknown tool with no negotiation or fallback.

`lsp_trace_v1_capabilities` is the MCP wire location for v1 capability and version discovery because MCP initialization provides no extension point this decision can rely on. It is read-only, always advertised, performs no publication or external I/O, and accepts exactly `{}`; its unversioned alias has the identical schema. Any member is a tool-schema validation error with no envelope. Its `COMPLETE/SUCCEEDED` envelope `result` is exactly `{"capabilities_version":"1","selected_envelope_version":"1","supported_envelope_versions":["1"],"tools":[ToolCapabilityV1,...],"selector_publication_supported":boolean,"inline_byte_limit":uint64,"list_page_max":uint32}`, with `additionalProperties:false`. `ToolCapabilityV1` is exactly `{"name":string,"aliases":[string,...],"input_schema_id":string,"envelope_schema_ids":[string,...],"artifact_schema_ids":[string,...],"availability":"NOT_IMPLEMENTED"|"CONTAINMENT_UNAVAILABLE"|"RUNTIME_DISABLED"|"ENABLED"}`, closed, and is used for every canonical implemented or reserved entry. Capability metadata is authoritative for reserved-name recognition, canonical names, aliases, current availability, and permitted schema identities. For each canonical tool at its current availability, `envelope_schema_ids` enumerates every and only envelope schema identity that the current binary may emit, and `artifact_schema_ids` enumerates every and only artifact-layer schema identity that any variant currently permitted for that tool and availability may carry through delivery or the explicitly permitted digest-only cases. Both arrays are ordered by schema-ID UTF-8 bytes, duplicate-free, bounded by the committed Stage 1 per-tool schema-ID maximum, and may be empty exactly when no such current identity exists. Every member is committed in the current accepted manifest, resolves through the current schema registry, and is applicable to calls handled by that binary in that availability state; no planned, future, uncommitted, unavailable, or inapplicable variant is included. For a `NOT_IMPLEMENTED` later-stage entry, the sets therefore contain only currently committed identities needed for valid known-but-unimplemented calls (normally only the `TOOL_NOT_IMPLEMENTED` envelope identity and an empty `artifact_schema_ids`). For a `CONTAINMENT_UNAVAILABLE` entry, they contain every and only committed variants callable in that state (normally only the `PROCESS_CONTAINMENT_UNAVAILABLE` envelope identity and an empty `artifact_schema_ids`), never enabled-handler, session-provenance, or future identities. A later-stage schema identity appears only through a newly accepted manifest and a new process started from the binary after that explicitly versioned schema and its manifest entry are committed. `name` is the canonical versioned name; `aliases` is bounded to `0..1`, ordered by UTF-8 bytes, contains no canonical name, and in v1 contains exactly the one unversioned alias listed above. Names, aliases, and schema IDs are nonempty and unique in their respective namespaces; entries are ordered by canonical-name UTF-8 bytes and use the committed Stage 1 bounds. `tools` contains all twelve canonical entries; `tools/list` is the exact projection with `availability:ENABLED`, counts canonical names only, and never includes aliases. Absence from `tools/list` means not advertised, not unknown. Recognition of either canonical or alias spelling resolves through the capability reserved/canonical/alias registry to the same immutable entry; a name is unknown only when it is absent from that registry. Limits are the effective process configuration. The complete result, including both schema-ID arrays and every availability value, is immutable for the MCP process lifetime: changing flags, compiled/accepted stages, schemas, versions, names, aliases, or bounds requires starting another process. Stage 1's schema registry, manifest, and exact golden transcript include this input and output schema, six `ENABLED` canonical offline entries, and six reserved `NOT_IMPLEMENTED` later-stage entries regardless of `--enable-live-lsp`; aliases add zero to the advertised count.

Every successful `COMPLETE` or `NOOP` operation is exactly one of two closed output kinds: `ENVELOPE_RESULT` or `ARTIFACT_DELIVERY`. `ENVELOPE_RESULT` requires a tool-defined, non-null structured value in envelope `result` and is never publication-eligible. `ARTIFACT_DELIVERY` carries exact artifact bytes either as inline envelope `content` or as a `publication_receipt` after publication to the caller-supplied selector; artifact-layer identity applies only to this kind and to the two explicitly permitted digest-only failure cases. V1 has no successful no-result variant: a stage schema may select only one of these two successful kinds and may not add, name, or imply a third kind or a successful variant without non-null `result` or artifact delivery. Error, cancellation, timeout, incomplete, and publication-error variants are outside the successful-kind taxonomy and obey the exhaustive outcome matrix below.

The classification is exhaustive:

| Canonical tool/output | Successful output kind | Selector publication | Identity layer |
|---|---|---|---|
| `lsp_trace_v1_capabilities` | `ENVELOPE_RESULT` | forbidden | envelope only; capability schema IDs are declarations, not delivered artifact identity |
| `lsp_session_v1_list`, `lsp_session_v1_status`, `lsp_session_v1_stop`, `lsp_session_v1_restart` | `ENVELOPE_RESULT` | forbidden | envelope only |
| `lsp_trace_v1_schema_get` | `ARTIFACT_DELIVERY` | eligible | artifact layer identifies the delivered schema bytes |
| `lsp_trace_v1_validate`, `lsp_trace_v1_verify`, `lsp_trace_v1_inspect`, `lsp_trace_v1_filter` | `ARTIFACT_DELIVERY` | eligible | artifact layer identifies schema-bearing delivered bytes; no identity when the existing artifact family has no declared artifact schema |
| `lsp_trace_v1_incoming`, `lsp_trace_v1_slice` complete, incomplete, or eligible interruption snapshot | `ARTIFACT_DELIVERY` | eligible | existing graph artifact layer; internal graph `schema_version` remains distinct |

Aliases inherit the canonical row and never define another output kind or identity. This classification changes neither native evidence authority nor custody: `result`, inline delivery, publication, receipts, and schema identity contribute no authority upgrade.

For every schema-bearing `ARTIFACT_DELIVERY` family, the applicable stage schema must specify a deterministic reversible mapping between envelope `content` JSON and the authoritative artifact bytes, either by an explicit byte-preserving encoding or a named canonical serialization. The exact mapping and its vectors remain stage-owned; this ADR selects no encoding. Schema validation, `artifact_digest`, `artifact_byte_length`, selector publication, and inline delivery all refer to those same authoritative bytes. Decoding or serialization failure is `DOMAIN_ERROR/FAILED/OUTPUT_VALIDATION_FAILED` before delivery or publication. For the same artifact, published bytes and the bytes recovered from inline `content` are byte-identical.

Large output publication reuses existing owner-only publication and selector-custody semantics. V1 exposes no MCP artifact resource and returns no server-chosen private filesystem path. The following `output_selector` contract is normative:

1. The caller supplies the selector. The host configures either one cleaned absolute permitted root that the manager opens and identity-verifies, or a policy callback. A successful callback must return an already-open pinned permitted-root directory capability whose identity the callback has verified against host policy, plus normalized relative path components beneath that capability. Returning only an authorization decision or ambient absolute path is forbidden; absent either permitted-root form, selector publication is disabled.
2. The selector is parsed lexically, must be non-empty, and must not contain NUL. With a configured root, a relative selector is normalized into relative components beneath that root. An absolute selector is accepted only as callback input when host policy allows it, and the callback must convert it to the pinned capability plus normalized relative components; callback-only ambient absolute path authorization is forbidden. Components must contain no empty, dot, dot-dot, root, separator, or platform-prefix element.
3. Before inspecting or creating components, the manager owns an identity-verified, owner-only pinned directory handle for the permitted root, whether opened from configured policy or returned by the callback. Every subsequent lookup, directory creation, temporary-file creation, and publication rename is component-relative to pinned directory handles, uses no-follow semantics, and rejects symlinks, non-directory parents, mount or identity substitution, and any inability to provide those guarantees with `OUTPUT_SELECTOR_UNSAFE`. Missing parents are created exclusively beneath a pinned parent with owner-only permissions and then opened and identity-checked without following links. V1 never re-resolves an accepted selector by ambient absolute path.
4. The final target must not exist. V1 has no overwrite mode. Publication exclusively creates an owner-only temporary sibling with mode `0600`, writes and syncs the exact marshaled bytes, closes it, and uses a component-relative atomic no-replace rename under the pinned final-parent handle. Atomic publication means namespace no-replace visibility, not directory-entry crash durability. V1 neither requires a destination-directory sync nor includes one in outcome or receipt semantics and makes no directory-entry crash-durability claim. An implementation should omit it; if a host attempts one after rename, it is best-effort hardening only, and its failure cannot change the already committed operation outcome, receipt, or claims. If the platform/filesystem cannot guarantee pinned component-relative no-follow traversal, exclusive creation, and atomic no-replace publication, selector publication fails closed with `OUTPUT_SELECTOR_UNSAFE`; a check-then-rename emulation is forbidden. A host may further restrict permissions but must not broaden them.
5. Before target coordination, every artifact-producing operation computes and validates the authoritative bytes, SHA-256 digest, fully frozen candidate success receipt, pinned target handles and normalized collision key, and prebuilds immutable success and `PUBLICATION_ERROR/PUBLICATION_FAILED` terminal envelopes/records. Live operations also capture the typed reservation plus immutable expected generation and lease identities. The receipt contains intended byte length, digest, schema identity where applicable, and prospective publication mechanism such as atomic no-replace. Its existence in memory is neither evidence of publication nor a success claim. It becomes an emitted receipt, covers exactly the published bytes, and gains the defined receipt meaning only when the operation-local arbiter installs the prebuilt terminal success envelope after rename. It contains neither the selector nor any server-chosen path. Envelope diagnostics must not echo the selector. The caller correlates the emitted receipt to its own request.
6. On failure, the manager closes and removes its temporary sibling by its pinned parent handle and reports bounded cleanup status. It never removes or alters a caller-existing final target. Startup may remove only stale temporary siblings bearing the implementation's private marker and satisfying the host retention policy, using the same pinned-handle and no-follow rules.

Every artifact-producing operation, offline or live, owns an operation-local atomic terminal/publication arbiter. Offline operations use it without a session or `event_seq`. Live operations first obtain the existing typed reservation and session-local ordering under the session mutex. After all authoritative publication material is prepared, a live operation, under session order, performs the final generation, lease, deadline, cancellation, poison, crash, and lifecycle eligibility checks, allocates the publication `event_seq`, and CASes its operation-local reservation to irrevocable `PUBLISHING`; an offline operation performs the equivalent request-local eligibility CAS without session state. This ticket is publication eligibility and the first-applicable cutoff: later cancellation, timeout, generation, lease, poison, crash, or session-lifecycle events may affect session state and bookkeeping but cannot rewrite that operation. For a live operation, the `event_seq` allocated by the successful `PUBLISHING` CAS is also the operation terminal's fixed ordering value and is retained in whichever prebuilt terminal record is subsequently installed; terminal installation is not a distinct session event and allocates no new operation `event_seq`. Any sequence allocated after target coordination is session bookkeeping only and cannot alter, replace, or reorder that operation terminal. Offline operations expose no session `event_seq`; their request-local CAS fixes the equivalent request-local terminal order. All session/lifecycle locks are then released.

Every selector publication is serialized by a process-local target coordinator keyed by the identity-verified final-parent filesystem object identity plus the platform-canonical final-component semantics, including applicable case, normalization, and alias rules. Path spelling and capability-instance identity are not key inputs: every pinned handle or selector resolving to the same final directory entry shares one process-local key. If stable equality cannot be established before the operation, publication fails closed with `OUTPUT_SELECTOR_UNSAFE`. No operation may wait for or acquire target coordination while holding a session/lifecycle mutex or any lock another path may acquire after target coordination. The target coordinator is universally outer. Under it, the operation validates only the immutable publication ticket, target identity, and candidate identity, then either installs the prebuilt publication-error terminal record without rename or performs the component-relative atomic no-replace rename and atomically installs exactly one prebuilt success terminal record through its operation-local arbiter. Target-exists and other no-replace rename failures install the prebuilt publication-error record. No session lock is acquired under coordination; coordination is released before session/lifecycle bookkeeping. Competing same-process publications to the same target therefore cannot interleave. This adds no cross-process serialization claim beyond atomic no-replace namespace visibility, and the admitted manager-death gap between rename and terminal installation or delivery remains unchanged.

A request whose result may exceed the inline limit should supply `output_selector`. If no selector is supplied and the result exceeds the limit, the operation fails closed with `OUTPUT_REQUIRES_SELECTOR` before emitting partial content. MCP must not invent a weaker temporary-file contract. Successful selector publication does not imply traversal success, source authenticity, or stronger evidence authority.

## Stage 2: lifecycle operations (not implemented)

Expose explicit lifecycle tools before live traversal:

```text
lsp_session_v1_list
lsp_session_v1_status
lsp_session_v1_restart
lsp_session_v1_stop
```

Lifecycle results disclose session state, key identity, age, last-use time, restart count, active-request count, and bounded health information. They do not expose environment values, raw unbounded stderr, source text, or hidden server data.

Lifecycle operations are scoped to sessions owned by the current MCP process and trust domain. There is no cross-process discovery or attachment in v1.

Before public live traversal is advertised, the repository provides one deterministic Stage 2 fake-language-server executable and conformance script that use the identical process, framing, manager, lifecycle, queue, lease, terminal-arbiter, and teardown paths used by Stage 3. The owning versioned Stage 2 scenario specification defines the exact script grammar, fixture mechanics, barriers, canonical ledgers, nondeterministic replacements, and scenario catalog. It must cover initialization, every public state, stop/restart, queued and active cancellation/timeout races, startup failures with and without a child, hangs, unexpected death, late/duplicate/unknown/wrong-generation responses, framing corruption, containment cleanup, rejection before capability publication or execution of profiles granting containment-disable, reconfiguration, escape, bypass, supervisor-control, or delegation authority, adversarial voluntary escape and descendant transfer/reparent/delegation attempts under every admissible granted permission/credential/capability, verification that external host/supervisor principals alone are outside the managed-process threat boundary, stderr truncation, death/reap ordering, reap failure, and no generation overlap. It uses no sleeps for ordering, wall-clock races, filesystem watchers, network, or host language server.

Every specified scenario emits a canonical event ledger, MCP transcript, child-process ledger, and final resource census. Repeated runs with the same script must be byte-identical after only specification-declared replacement of nondeterministic fields. This harness is not an MCP tool and grants no production capability. Stage 2 acceptance depends on that versioned executable scenario specification and its complete matrix rather than on empty `list` output.

## Stage 3: live traversal operations (not implemented)

After lifecycle acceptance, complete the planned MCP v1 surface by exposing:

```text
lsp_trace_v1_incoming
lsp_trace_v1_slice
```

Each request must supply an explicit workspace and exactly one named profile. Caller-supplied commands, arguments, environment, language configuration, or resolved server configurations are forbidden. Automatic selection from file extension, language ID, source path, workspace content, or any unnamed profile is forbidden in v1. A process's resolved command, arguments, environment references and values, language configuration, trust domain, workspace identity, and server-affecting options are immutable for its lifetime; any change selects a distinct key or requires restart into a newly resolved generation.

The tools return the same graph schemas, structured incomplete-evidence distinctions, diagnostics, and publication behavior as the corresponding CLI commands. MCP success is not substituted for graph completion status.

Lifecycle schemas remain the separate exact schemas below and accept none of these traversal fields.

## Transport boundary

V1 uses MCP over stdio.

The hosting MCP client owns process launch, transport access, and any user authentication or authorization around that launch. LSP Trace does not claim that MCP transport authenticates requests or evidence.

Network transports, remote multi-tenant service operation, and shared daemon discovery are deferred. Adding any of them requires a separate authentication, authorization, isolation, and threat-model decision.

## Persistent session identity

A reusable session key is the digest of one exact versioned canonical byte encoding. `SessionKeyEncodingV1` starts with ASCII `lsp-trace/session-key`, octet `00`, and version octets `00 00 00 00 00 00 00 01`. Every value is `tag:u8 || length:uint64_be || payload`; tags are closed in v1: null `00`, false `01`, true `02`, unsigned integer `03`, signed integer `04`, bytes `05`, UTF-8 string `06`, path `07`, list `08`, map `09`, language configuration `0a`, and server-affecting options `0b`. Fields occur exactly in this order: trust-domain identity, canonical workspace identity, selected profile name, resolved command, ordered arguments, environment entries, language configuration, and server-affecting options. Any tag, field, or ordering change requires a new encoding version.

Strings are Unicode NFC followed by strict UTF-8; invalid Unicode is rejected. Bytes are unchanged. Boolean and null payloads are empty because their tags carry the value. Unsigned zero is one octet `00`; every other unsigned integer is the shortest unsigned big-endian magnitude with no leading `00`. Signed zero is one octet `00`; every signed integer is the shortest two's-complement big-endian sequence whose first bit preserves the sign: positive values receive one leading `00` exactly when needed to prevent a negative interpretation, and negative values drop leading `ff` octets exactly while the next octet's high bit remains one. Lists preserve order and have payload `count:uint64_be || encoded-item...`. Maps have payload `count:uint64_be || encoded-key || encoded-value...`, sorted lexicographically by complete encoded-key bytes; duplicate encoded keys are forbidden. Language configuration is tag `0a` around a map with exactly the NFC string keys `language_id`, `initialization_options`, and `workspace_configuration`; options is tag `0b` around a map whose keys are the closed profile-defined server-affecting option names. Their nested values use only these canonical forms. Floating point, aliases, omitted-versus-null coercion, and implementation-dependent scalar encodings are forbidden.

A path payload is the NFC UTF-8 encoding of the cleaned absolute lexical path, with separators converted to `/`, `.` removed, `..` resolved without crossing the root, and no trailing slash except a root. POSIX roots retain `/` and POSIX case bytes are preserved. Windows drive paths use uppercase drive letter plus `:/` and preserve all remaining component case; UNC paths use `//` plus NFC server/share/components and preserve case. Device paths, alternate data streams, drive-relative paths, and unresolved prefixes are rejected. No case folding or filesystem identity lookup occurs in this byte encoding; therefore paths that a case-insensitive filesystem treats as aliases can intentionally have different v1 session identities, and POSIX and Windows canonical identities are intentionally not cross-platform equal.

Normative complete-value golden vectors use spaces only for readability: null `00 0000000000000000`; false `01 0000000000000000`; true `02 0000000000000000`; unsigned zero `03 0000000000000001 00`; unsigned 255 `03 0000000000000001 ff`; unsigned 256 `03 0000000000000002 0100`; signed zero `04 0000000000000001 00`; signed 127 `04 0000000000000001 7f`; signed 128 `04 0000000000000002 0080`; signed -1 `04 0000000000000001 ff`; signed -129 `04 0000000000000002 ff7f`; NFC string `é` `06 0000000000000002 c3a9`; POSIX path `/a/b` `07 0000000000000004 2f612f62`; Windows path `C:\\A\\b` `07 0000000000000006 433a2f412f62`; UNC path `\\\\Srv\\Share\\x` `07 000000000000000d 2f2f5372762f53686172652f78`; list `[false,true]` `08 000000000000001a 0000000000000002 010000000000000000 020000000000000000`. The top-level payload is the direct concatenation, with no enclosing list, map, count, or separator, of the eight complete encoded values in the field order above. The schema/transcript manifest contains complete top-level key vectors with fixture-fixed `K_process`, environment HMACs, language/options maps, final encoding bytes, and SHA-256, including zero, signed-boundary, POSIX, drive, UNC, and rejected Windows-path cases.

Environment reference names are sorted by their canonical UTF-8 bytes. The per-name domain is exactly the UTF-8 bytes of ASCII `lsp-trace/environment-entry/v1`, followed by octet `00`. Each environment entry is one canonical two-item list `[encoded name value, encoded runtime-value value]` for HMAC input and one canonical two-item list `[encoded name value, encoded 32-byte HMAC value]` in the retained entries container; thus framing is supplied by the canonical value encodings and list counts. Its digest is `HMAC-SHA-256(K_process, domain || encoded_name || encoded_runtime_value)`; raw runtime values are never retained. The ordered environment entries container is a canonical list in sorted-name order. Its process-context domain is exactly the UTF-8 bytes of ASCII `lsp-trace/process-context/v1`, followed by octet `00`, and the environment top-level value is the encoded 32-byte result of `HMAC-SHA-256(K_process, process_context_domain || encoded_entries_list)`.  `K_process` is generated process-locally, retained only in protected memory for that MCP process, and is never returned, logged, persisted, or exposed through schemas. The keyed construction avoids representing a digest as concealment by an unkeyed hash, especially for low-entropy secrets; it does not make session identity an authentication claim.

`SessionKey = SHA-256(SessionKeyEncodingV1)`, represented as lowercase hexadecimal with the `sha256:` prefix. Two inputs are equal for reuse only when their complete `SessionKeyEncodingV1` bytes are equal within the same manager process; digest equality is an indexed candidate and must be confirmed by canonical-byte equality. Different encoding versions are never equal or reusable. A future reader may decode a recognized version but must reject unknown versions; changing field order, normalization, scalar encoding, environment digest composition, or equality semantics requires a new encoding version. Because `K_process` is process-local, keys are intentionally not comparable across manager processes.

A session may be reused only when every key component matches exactly. A request with a different workspace, profile, command, arguments, environment identity or runtime value, language configuration, trust domain, or server-affecting option receives a different session.

The key identifies a process/configuration reuse boundary. It does not prove source identity, server correctness, semantic equivalence, or independent corroboration.

## Workspace identity and snapshot ceiling

Canonical workspace identity uses the cleaned absolute workspace path plus the same explicit identity rules documented for CLI invocation. Symlink aliasing limitations remain explicit unless a later decision changes them.

A persistent session does not assert one immutable workspace snapshot across requests. For every graph artifact:

- retain the persistent session ID and session generation;
- retain directly resolved seed URI/content-digest pairs;
- retain existing process-context identities;
- retain the request's resolved server configuration and bounds;
- mark source-graph completeness according to existing semantics;
- make no claim about unobserved workspace files.

File-watcher delivery, server indexing, and cache state are process observations, not source custody. The artifact must not imply that all workspace changes were observed merely because the session remained healthy.

## Session lifecycle

Sessions start lazily on the first live request for a new key, but only after the manager has consumed a closed process-lifetime containment probe result before capability publication. That internal result is exactly `VERIFIED` or `UNAVAILABLE(reason, failed_check)`. `VERIFIED` attests the supported primitive/profile identity, independently enforced bounded owner-death cleanup without manager teardown code, complete coverage of the server and every descendant, prevention of escape, transfer/reparenting, or delegation around containment under every admissible granted authority, and absence of any granted containment-control, reconfiguration, escape, bypass, or delegation authority. Any unsupported, indeterminate, failed, mutable, or incomplete check is `UNAVAILABLE` and maps to immutable process-lifetime `CONTAINMENT_UNAVAILABLE`: persistent lifecycle and live tools are omitted from `tools/list`, and no session/server is selected, allocated, started, or executed. The probe result is internal, bounded, and non-authoritative, and exposes no sensitive credential or path. External principals that control the host or supervisor remain outside the managed-process threat boundary without weakening descendant coverage; v1 excludes only genuinely unrelated or pre-existing processes that never descended from the managed generation. Exact OS enumeration, evidence, mechanics, timing, reap/survivor verification, authority-admissibility checks, and adversarial fixtures remain Stage 2-owned.

The manager also owns one process-local monotonic `manager_event_seq`. It allocates the next value under the manager ordering lock for every event that can order or compare work across sessions, including request receipt/admission, capacity decisions and re-evaluations, session creation, last use, terminal retention, victim reservation/removal, and list snapshot creation. Request receipt obtains this sequence before any admission validation, session mutex, capacity semaphore, queue slot, or startup/reap barrier. Values are unique and never compared across manager processes; exhaustion fails closed before admitting new work. Session-local `event_seq` remains the sole race order within one session and is never compared across sessions.

Each session has:

- an opaque process-local session ID;
- an immutable session key;
- a monotonically increasing generation number;
- lifecycle state;
- creation, last-use, and idle-expiry times;
- bounded request and stderr correlation state;
- restart count;
- active-request count.

A session generation increments whenever its language-server process restarts. Graph provenance records both session ID and generation so artifacts from before and after a restart cannot be mistaken for one uninterrupted process observation.

### Generation and request identity contract

For one manager process, `SessionID` is opaque and unique. `Generation` is a positive, monotonically increasing integer scoped to that session. After final generation binding, a manager request identity is `(SessionID, Generation, ManagerRequestID)`, where `ManagerRequestID` is manager-process unique. Before that binding, an unpinned live admission attached to a restart intent is identified by `(SessionID, RestartIntentID, ManagerRequestID)` and cannot dispatch, own an LSP ID, acquire a document lease, or produce generation provenance. An LSP request identity is `(SessionID, Generation, LSPRequestID)`, and an ID is never reused within its generation.

Each admitted manager request owns an ordered generation-local relation `LSPRequests(manager) = [(ordinal, lsp_request_id, response_state, cancel_state, events)]`. Ordinals are contiguous positive integers in dispatch order. `response_state` is exactly `UNRESOLVED`, `RESPONDED`, or `TOMBSTONED`; `cancel_state` is independently exactly `NOT_REQUESTED`, `SENT`, or `WRITE_FAILED`. `events` contains the ordered `event_seq` references for dispatch, response, cancel attempt/result, and tombstone creation when present. A successful complete request-frame write appends `(UNRESOLVED,NOT_REQUESTED)` at that dispatch event. A valid matching response changes only `UNRESOLVED→RESPONDED`; a response after `SENT` or `WRITE_FAILED` is still accepted and recorded as `RESPONDED`, consumed as an intermediate response, and cannot reverse a manager cancellation/timeout winner. Cancellation/timeout visits every `UNRESOLVED` entry in ordinal order: a complete cancel-frame write changes `NOT_REQUESTED→SENT`, and a failed write changes `NOT_REQUESTED→WRITE_FAILED`; neither changes `response_state`. Repeated cancellation never rewrites either terminal cancel result. Queued or admission-failed work has an empty relation.

When a manager request terminalizes, each still-`UNRESOLVED` identity atomically changes to `TOMBSTONED` at its tombstone-creation event and enters the bounded generation-local tombstone container; cancellation is not required for tombstone creation. A matching late response consumes and retires that tombstone and is discarded without reopening the manager result. Tombstones never block the next queue head. Duration eviction is applied first at each event using `(expires_at,creation_event_seq,lsp_request_id_bytes)`; count eviction then removes oldest `(creation_event_seq,lsp_request_id_bytes)` until the configured bound holds. At either eviction, the exact retired identity is deliberately forgotten. Any later response matching no retained active or tombstone identity is `UNKNOWN_LSP_RESPONSE` and poisons that generation; there is no attempt to distinguish expired-late from never-issued IDs.

Public envelopes never expose a singular LSP ID. Diagnostic schemas either omit LSP identity or contain `lsp_requests`, an ordered, bounded summary of `{ordinal,response_state,cancel_state,event_refs}` and, only when policy permits, `lsp_request_id`; `event_refs` names only present ordered event kinds and sequences, and truncation includes total/retained counts and omitted ordinal range. Complete ledgers, provenance fixtures, goldens, and transition tests record both orthogonal states, every cancellation write result, response-after-cancel, tombstone creation/consumption/eviction, the manager-to-many relation, and generation ownership.

A live admission with an explicit `generation` precondition binds to that exact generation at admission. An unpinned admission to an existing `READY` session binds to its current generation at admission. An unpinned admission that encounters `STOPPED`, `CRASHED`, or fully reaped `POISONED` does not bind to the predecessor generation; it provisionally attaches to the exact typed `RESTART` intent as specified below. After final binding, the manager must compare the bound generation with the session's current generation at enqueue, immediately before dispatch, when accepting a response, before committing an artifact or publication, and before terminalization. A mismatch loses the relevant race: no dispatch, response acceptance, artifact commit, or success terminalization occurs, and the terminal arbiter selects `STALE_GENERATION` unless an earlier terminal outcome already won. Unknown, duplicate, or wrong-generation LSP response IDs poison only the generation that read them. An identifiable late response for an already-terminal request is discarded and recorded.

Generation `n+1` must not be allocated, exposed, initialized, or receive work until generation `n` has both an observed process-death event and a successful child-reap result. A timeout or recorded forced-termination attempt is not sufficient. Reap failure leaves the session `POISONED`, makes restart fail with `SESSION_REAP_INCOMPLETE`, and forbids generation overlap.

### Closed public state machine

The public `state` value is exactly one of `STARTING`, `INITIALIZING`, `READY`, `DRAINING`, `STOPPING`, `STOPPED`, `CRASHED`, or `POISONED`. Implementations may use private substates but must project them to one of these values. Public transitions are closed by this table; every other transition is an invariant violation and transitions to `POISONED` when a live process may remain.

| From | Event/guard | To | Required action |
|---|---|---|---|
| absent | first start accepted; process-lifetime containment result is `VERIFIED` | `STARTING` | allocate generation 1 and spawn inside the attested boundary; no predecessor death or reap is required |
| `STOPPED`, `CRASHED`, `POISONED` | restart accepted; retained predecessor generation death and reap confirmed | `STARTING` | allocate the next generation and spawn |
| `STARTING` | child pipes established | `INITIALIZING` | send `initialize` |
| `STARTING` | spawn/pipe failure before any child exists | `STOPPED` | retain bounded startup diagnosis; no process death is claimed |
| `STARTING` | pipe/setup failure after a child exists | `STOPPING` | retain bounded startup diagnosis; terminate, observe death, and reap before restart |
| `STARTING`, `INITIALIZING` | `STOP` or `RESTART` intent accepted; no child exists | `STOPPED` | retain the typed intent and startup diagnosis; terminalize `STOP`, or begin the retained `RESTART` successor only from `STOPPED` |
| `STARTING`, `INITIALIZING` | `STOP` or `RESTART` intent accepted; a child exists or may exist | `STOPPING` | retain the typed intent; discard any later initialization response, perform bounded teardown, observe death, and reap before `STOPPED` |
| `INITIALIZING` | valid initialize response and `initialized` sent | `READY` | open admission |
| `INITIALIZING` | timeout, protocol/sync failure | `POISONED` | close admission; begin teardown |
| `READY` | graceful stop/restart/idle eviction accepted with active or queued work | `DRAINING` | close admission; terminalize queued work; cancel or bound active work |
| `READY` | graceful stop/restart/idle eviction accepted with no work | `STOPPING` | begin shutdown |
| `DRAINING` | active and queued count reaches zero | `STOPPING` | begin shutdown |
| `STARTING`, `INITIALIZING`, `READY`, `DRAINING` | child exits unexpectedly | `CRASHED` | close admission; terminalize work; reap |
| `STARTING`, `INITIALIZING`, `READY`, `DRAINING`, `STOPPING` | poison predicate | `POISONED` | close admission; terminalize work; force bounded teardown |
| `STOPPING` | process death and reap confirmed | `STOPPED` | invalidate generation-local state |
| `CRASHED`, `POISONED` | process death and reap confirmed | same state | retain terminal diagnosis; allow explicit/lazy restart |

`CRASHED` is reserved exclusively for observed unexpected process death when no earlier poison diagnosis exists. Spawn failure before a child exists and pipe setup failure before child execution return the session to `STOPPED` with a retained bounded startup diagnosis and do not claim death. If pipe setup or another partial-start failure occurs after a child exists, the session projects `STOPPING` until death is observed and reap succeeds, then `STOPPED`; restart cannot allocate a generation before both events. For initialization completion racing an accepted `STOP` or `RESTART`, the lower `event_seq` wins: intent acceptance first keeps its kind and retained result, forbids `READY`, and discards or race-orders the initialize response as a teardown diagnostic; initialization completion first reaches `READY`, after which the already-accepted intent follows the `READY` row without changing kind or result. No-child acceptance reaches `STOPPED` directly; possible-child acceptance cannot reach `STOPPED` until death and reap. A `RESTART` successor is allocated only afterward. `POISONED` means protocol or manager state is unsafe or uncertain, whether its process is still alive or later dies. A poison predicate ordered before a later death preserves `POISONED`; the death is retained as teardown evidence and does not overwrite the poison diagnosis. An unexpected death ordered first produces `CRASHED` and is not itself a poison predicate. Neither state permits admission. A stopped session remains listable until deterministic retention eviction.

Sessions stop when explicitly requested, when idle expiry is reached, when resource policy evicts them, when the MCP server exits, when the independently enforced containment primitive observes manager death or owner close, or when an unrecoverable lifecycle failure occurs.

A lifecycle intent is generation-bound and has `(intent_id,kind,target_generation,successor_generation?,state,result,created_event_seq,terminal_event_seq?)`, where `kind` is exactly `STOP`, `RESTART`, or manager-internal `EVICT`; no public tool inserts or directly joins `EVICT`. Intent insertion is its linearization point and irrevocably closes ordinary admission; intent execution then continues independently of every caller attachment through queued-work terminalization, bounded active-work handling, shutdown/exit, containment teardown, death observation, reap, and (for `RESTART`) exactly one successor startup. `successor_generation` is absent until predecessor death and reap permit allocation and is immutable once allocated. A caller has a separate terminal arbiter and immutable deadline. Join and conflict rules apply only while the incumbent intent is nonterminal. Same-kind callers attach to that nonterminal intent only after generation-compatible resolution: the caller's selector and optional `generation` precondition must resolve to the incumbent intent's immutable `target_generation` (the predecessor generation for both `STOP` and `RESTART`); a mismatch returns `STALE_GENERATION` without mutation or attachment. An omitted generation is not a wildcard: the selector is resolved at the join linearization point and joins only if that resolved generation equals the incumbent target. Compatible callers await the retained result subject to their own deadlines; timeout or transport cancellation atomically detaches and terminalizes only that caller and never cancels, changes, or delays the intent. A conflicting kind returns `LIFECYCLE_CONFLICT` only against a generation-compatible nonterminal incumbent; stale resolution wins as `STALE_GENERATION` with no attachment.

Terminal intent succession has one rule: after an intent terminalizes, it leaves bounded immutable history ordered by `(terminal_event_seq,intent_id)` until session-record removal, ceases to be incumbent, and never blocks insertion of a later legal different-kind intent. A later caller may receive a retained terminal result without insertion only where the operation/state table explicitly selects same-kind replay and its selector resolves generation-compatibly to that history entry; otherwise normal state legality determines whether a new intent is inserted. `status` reports at most one current nonterminal intent separately from the bounded retained terminal-history summary; terminal history is never projected as an incumbent. This is retention and selection over the existing intent states, not a second operation state machine. Lazy unpinned live restart callers may attach only to a nonterminal exact `RESTART`; after it terminalizes, only an explicitly selected generation-compatible same-kind replay may use its result.

`lsp_session_v1_list` (and its `lsp_session_list` alias) is bounded and non-cancellable after successful schema/cursor validation: it snapshots at one event, performs only bounded in-memory filtering/sorting/paging under `configured_list_max`, and returns without session, process, publication, or external I/O waits. Cancellation observed before validation completes yields no envelope under MCP validation handling; no list timeout code exists. This exemption is justified by the fixed work bound and avoids a meaningless lifecycle attachment.

The shared intent executor removes queued requests with `SESSION_STOPPING`, applies the bounded active policy, attempts LSP `shutdown`, sends `exit` when possible, closes stdin, escalates through containment deadlines, closes pipes, finishes bounded stderr draining, observes death, and reaps. Teardown after transport shutdown begins is exempt from `didClose`; leases are invalidated without attempting it. A graceful-shutdown failure cannot leave the generation reusable, and a restart successor begins only after death and reap. The first applicable row by `event_seq` fixes the retained intent result; all attached and later compatible joined callers observe that same result.

| Teardown phase/condition | Public state and retained diagnosis | Retained `STOP` / `RESTART` / `EVICT` result | Successor forbidden? |
|---|---|---|---|
| `shutdown` request timeout or protocol failure | `POISONED`; bounded shutdown diagnosis | each `DOMAIN_ERROR/FAILED/SESSION_POISONED` | yes |
| `exit`, stdin close, or pipe close failure making protocol/transport state unsafe | `POISONED`; bounded I/O diagnosis | each `DOMAIN_ERROR/FAILED/SESSION_POISONED` | yes |
| terminate or kill failure, or death-observation timeout | `POISONED`; bounded signal/survivor diagnosis; death unconfirmed | each `DOMAIN_ERROR/FAILED/SESSION_REAP_INCOMPLETE` | yes |
| survivor containment failure | `POISONED`; bounded survivor identities; containment death unconfirmed | each `DOMAIN_ERROR/FAILED/SESSION_REAP_INCOMPLETE` | yes |
| stderr drain failure after otherwise bounded teardown | `POISONED`; bounded drain/truncation diagnosis | each `DOMAIN_ERROR/FAILED/SESSION_POISONED` | yes |
| reap failure after observed death | `POISONED`; death observed, reap unconfirmed | each `DOMAIN_ERROR/FAILED/SESSION_REAP_INCOMPLETE` | yes |
| death observed, containment has no survivors, stderr drain complete, and reap succeeds | `STOPPED`; retain prior bounded teardown diagnosis until the applicable intent action completes | `STOP`: `COMPLETE/SUCCEEDED`; `RESTART`: continue the same retained intent to one successor; `EVICT`: freeze `COMPLETE/SUCCEEDED`, remove the victim session record, and release its capacity reservation | no, but `RESTART` allocates only now |

This table is exhaustive for teardown completion. Protocol-unsafety selects `POISONED`/`SESSION_POISONED`; inability to confirm containment death or reap selects `POISONED`/`SESSION_REAP_INCOMPLETE`. When a child existed, `STOPPED` is forbidden until death, zero contained survivors, stderr drain completion, and reap success are all established.

### Total event order and terminal arbiter

Each session owns a monotonic `event_seq`. Under the session mutex, every lifecycle, queue, lease, synchronization, dispatch, response, cancellation, timeout, process, poison, artifact, and terminal event receives the next sequence number. This is the total order used to resolve races within that session; wall-clock timestamps are diagnostic only. Cross-session list, last-use, victim, retention, admission, and capacity ordering uses only `manager_event_seq`; a fixture or implementation must never compare one session's `event_seq` with another's. The normative linearization points are:

| Operation | Linearization point |
|---|---|
| admission | explicit-pin generation/state validation, ready-generation binding, or provisional exact-`RESTART`-intent attachment plus manager-request insertion at one `event_seq` |
| restart successor binding | when that exact intent alone reaches `READY`, atomically bind every still-attached unpinned live request to its immutable successor generation at one `restart_bind_event_seq` |
| document lease/sync | lease acquisition or revalidation plus committed `didOpen`/`didChange` write event |
| enqueue | queue ownership insertion |
| dispatch | successful complete LSP frame write and append of the next owned `(ordinal,LSPRequestID,UNRESOLVED,NOT_REQUESTED,events)` entry |
| LSP response event | valid retained active/tombstone identity and generation classification, response-state update or tombstone consumption; never manager-terminal reservation |
| partial snapshot commit | while arbiter is `OPEN`, validation and immutable request-owned byte commit at one `event_seq`; no terminal reservation |
| normal response reservation | completed-output validation and CAS `OPEN → RESERVED_RESPONSE` |
| cancel/timeout selection | CAS `OPEN → RESERVED_CANCEL` or `OPEN → RESERVED_TIMEOUT`, atomically selecting the latest eligible pre-winner snapshot or none |
| stop/restart/evict intent | insert a typed nonterminal generation intent, or attach a same-kind caller to that nonterminal intent; a conflicting kind fails without attachment; retained terminal history is selected only by an explicit same-kind replay row and otherwise cannot block a later legal insertion |
| crash | ordered unexpected child-death observation; before the operation-local `PUBLISHING` CAS it is an applicable request conversion event |
| poison | first ordered poison predicate; before the operation-local `PUBLISHING` CAS it is an applicable request conversion event |
| generation/lease invalidation | first failed ordered generation or lease eligibility check before the operation-local `PUBLISHING` CAS |
| publication eligibility | live: under the session mutex, perform final generation/lease/deadline/cancellation/poison/crash/lifecycle checks, allocate the publication `event_seq`, and CAS the typed operation reservation to irrevocable `PUBLISHING`; offline: perform the equivalent request-local CAS without session state; this ticket is the first-applicable cutoff |
| publication terminal installation | after locks are released and the universal outer target coordinator is acquired, validate only immutable ticket/target/candidate identity; failure before rename or atomic no-replace failure installs the prebuilt publication-error record, while successful rename atomically installs the prebuilt success record through the operation-local arbiter; installation is not a distinct session event, allocates no new operation `event_seq`, and retains the live publication `event_seq` already fixed by the successful `PUBLISHING` CAS (or the equivalent request-local order for offline work); the admitted manager-death boundary remains between rename and terminal installation/delivery |

Every artifact-producing operation has one operation-local CAS-like terminal/publication arbiter initially `OPEN`; for live operations it incorporates the existing typed terminal reservation, while offline operations use it without session state or `event_seq`. Traversal may commit any number of immutable schema-valid request-owned partial snapshots while a live arbiter remains `OPEN`; committing a snapshot does not reserve the terminal result. Ordinary LSP responses, including intermediate responses used by multi-request traversal, are protocol events and likewise do not reserve it.

Normal completed output alone may CAS `OPEN → RESERVED_RESPONSE`. A cancel or timeout contender instead CASes `OPEN → RESERVED_CANCEL` or `RESERVED_TIMEOUT` and in the same ordered event selects the latest snapshot with `snapshot_event_seq < winning_event_seq`, or records `none`; all other contenders lose. The interruption owner includes the selected bytes inline when within the inline ceiling. For selector delivery it alone validates and publishes those bytes, then finalizes `CANCELLED/REQUEST_CANCELLED` or `TIMED_OUT/REQUEST_TIMEOUT`. With no selected snapshot, it performs no publication and finalizes without artifact fields. Interruption publication failure converts that same reservation to `PUBLICATION_ERROR/PUBLICATION_FAILED`, with the intended snapshot digest/length and bounded failure metadata; it never falls back to an interruption success or a different snapshot. Normal and interruption reservations cannot coexist.

Before target coordination, the sole reservation owner computes and validates the authoritative bytes, digest, fully frozen candidate receipt, pinned target handles and normalized collision key, and prebuilds immutable success and publication-error terminal envelopes/records. A live owner also captures its typed reservation and expected generation and lease identities. The collision key is derived from the identity-verified final-parent filesystem object identity plus the platform-canonical semantics of the final component, including applicable case, normalization, and alias rules; it is not derived from path spelling or capability-instance identity. Every pinned handle or selector that resolves to the same final directory entry must share one process-local key. If stable equality cannot be established, publication fails closed as `DOMAIN_ERROR/FAILED/OUTPUT_SELECTOR_UNSAFE` with no rename. Any receipt-construction or output-validation failure likewise performs no rename; a completed output validation failure finalizes as `DOMAIN_ERROR/FAILED/OUTPUT_VALIDATION_FAILED` with bounded diagnostics and no artifact fields.

For a live operation, under the session mutex and session order, the owner performs the final generation, lease, deadline, cancellation, poison, crash, and lifecycle eligibility checks, allocates the publication `event_seq`, and CASes the typed operation reservation to irrevocable `PUBLISHING`. An offline operation performs the equivalent request-local eligibility CAS without session state. This immutable ticket is both publication eligibility and the first-applicable cutoff. Later session or caller events cannot rewrite the operation. The operation then releases every session/lifecycle lock.

No operation may wait for or acquire the process-local target coordinator while holding a session mutex, lifecycle mutex, or any other lock that another path may acquire after target coordination. The target coordinator is universally outer in the lock order. While holding it, the operation validates only immutable ticket, target, and candidate identity; it performs no session-state revalidation and acquires no session lock. Failure before rename installs exactly one prebuilt `PUBLICATION_ERROR/PUBLICATION_FAILED` terminal record through the operation-local arbiter. Atomic no-replace rename failure, including target existence, does the same. Successful rename atomically installs exactly one prebuilt success terminal record through that arbiter. The operation releases target coordination before reacquiring session or lifecycle locks for bookkeeping. This prevents same-target interleaving across sessions and offline operations within one process, without claiming cross-process serialization beyond atomic no-replace namespace visibility.

Mere existence of the candidate receipt in memory is neither evidence that rename succeeded nor a success claim, and its publication fields describe only the prospective mechanism. The admitted process-death boundary remains between rename and terminal installation or delivery. Only successful terminal installation after rename makes the candidate an emitted receipt. No manager-controlled fallible envelope or record construction, serialization, digesting, or allocation occurs after rename; all such work is prebuilt before eligibility and coordinator entry. Unavoidable runtime, OS, or transport death remains the admitted gap. An externally observable terminal MCP outcome means an outcome delivered through the v1 protocol; target-file existence is excluded. If the manager dies after rename but before terminal-record append or protocol delivery, the caller target may exist without an externally observable outcome. The terminal record is process-local and in-memory unless a later accepted surface selects durable storage; v1 provides no cross-process recovery, cannot determine success afterward through protocol state, emits no synthesized or recovered outcome, and performs no overwrite, deletion, or republication. Any recovery/reporting operation remains deferred to a separately accepted later versioned surface. Selector and server-chosen path remain forbidden in responses and diagnostics. A cancel/timeout winner before dispatch still removes queue ownership, sends no LSP traffic, selects no snapshot, and finalizes with `CANCELLED_BEFORE_DISPATCH` or `REQUEST_TIMEOUT`. Terminal append uniqueness remains at most one, with exactly one terminal record and externally observable outcome when the manager survives through append and delivery.

### Public lifecycle selectors and results

Lifecycle input JSON Schemas are exact (`additionalProperties:false`). `lsp_session_v1_list` (and its `lsp_session_list` alias) accepts `{ "states"?: PublicState[], "limit"?: uint32, "after"?: string }`; `states` is nonempty and duplicate-free when present, `limit` is `1..configured_list_max`, and `{}` means all retained states with the configured maximum. `after` is an opaque manager-issued cursor bound to the exact filter, ordering version, and a retained list snapshot; malformed, expired, or filter-mismatched cursors return `LIST_CURSOR_INVALID`. Status, stop, and restart accept `{ "selector": {"session_id": string} | {"session_key": SessionKeySelectorV1}, "generation"?: uint64 }`, where the selector union has exactly one member and `generation` is a distinct top-level precondition.

`SessionKeySelectorV1` is the closed object `{ "version":"1", "trust_domain":string, "workspace":string, "profile":string, "server_affecting_options":[SessionKeyOptionV1,...] }`, with all four members required and `additionalProperties:false`. Strings are strict UTF-8 and NFC; `trust_domain` and `profile` are 1..256 UTF-8 bytes and `workspace` is 1..4096 UTF-8 bytes before the path normalization defined by `SessionKeyEncodingV1`. `server_affecting_options` has 0..64 entries, sorted by canonical option-name UTF-8 bytes with no duplicate name. `SessionKeyOptionV1` is exactly `{ "name":string, "value":SessionKeyOptionValueV1 }`, closed, with a 1..128-byte NFC name. `SessionKeyOptionValueV1` is a closed tagged union containing exactly one member: `{"null":true}`, `{"bool":boolean}`, `{"uint":uint64}`, `{"int":int64}`, `{"string":string}`, `{"bytes_base64":string}`, `{"list":[SessionKeyOptionValueV1,...]}`, or `{"map":[SessionKeyOptionV1,...]}`. Strings and decoded bytes are at most 4096 bytes; lists and maps have at most 64 entries; maps use the same sorted unique-name rule; total nesting depth is at most 8 and total decoded selector size is at most 64 KiB. Base64 is canonical RFC 4648 with padding. No omitted/null coercion, floating point, unknown tag, or unknown field is accepted.

Mapping is deterministic: `trust_domain`, normalized `workspace`, and `profile` become the first, second, and third top-level `SessionKeyEncodingV1` values; the manager resolves the fourth through seventh values (command, ordered arguments, environment entries including runtime-value HMAC composition, and language configuration) from current trusted profile/process configuration; selector `server_affecting_options` becomes the eighth value as tag `0b` around a map keyed by each option `name`, recursively converting the tagged selector value to the corresponding canonical null/bool/unsigned/signed/string/bytes/list/map value. The manager rejects any selector option not caller-visible and permitted by the selected profile. Runtime environment values, environment references, HMACs, `K_process`, resolved command/arguments/language configuration, and session-key digests are manager-resolved and absent from caller input.

Normative selector example: `{"version":"1","trust_domain":"local","workspace":"/work/repo","profile":"gopls","server_affecting_options":[{"name":"analysis_mode","value":{"string":"strict"}},{"name":"memory_mb","value":{"uint":512}}]}`. The Stage 2 schema/transcript manifest must include this exact selector and a mapping fixture showing its first three and eighth encoded values, fixture-resolved fourth through seventh values, complete `SessionKeyEncodingV1` bytes, and resulting digest. Resolution failure uses the applicable profile/input code and cannot select by workspace prefix, profile name alone, recency, caller-supplied secret, HMAC, or digest.

A syntactically valid selector that resolves to no retained session returns `isError:true`, `DOMAIN_ERROR/FAILED/SESSION_NOT_FOUND`. A mismatched `generation` returns `STALE_GENERATION` without mutation. For live admission, an explicit `generation` precondition never inserts or joins a restart intent and never rebinds: it operates only when that exact generation is current and `READY`, otherwise it returns `STALE_GENERATION`. Stop, restart, and eviction use the single intent/attachment contract above; no lifecycle tool may implement a second operation state machine.

The following table is the exhaustive normative projection for exact-selector `status`, `stop`, and `restart`. “Reaped” for terminal diagnoses means predecessor death was observed and reap succeeded; `STOPPED` is necessarily reaped or no-child. Before any row, selector absence yields `SESSION_NOT_FOUND` and a supplied generation mismatch, including a same-kind nonterminal incumbent whose target differs, yields `STALE_GENERATION`, both without mutation or attachment. Caller cancellation/timeout after attachment detaches only that caller with `REQUEST_CANCELLED`/`REQUEST_TIMEOUT`; the intent and other callers continue. A compatible same-kind nonterminal incumbent is joined; a different-kind nonterminal incumbent yields `LIFECYCLE_CONFLICT`. Retained terminal history is not incumbent: only the table's explicit compatible retained-result cases replay it, and it never prevents a later legal different-kind insertion. These caller outcomes do not alter the state-transition table.

| State | `status` (never mutates) | `stop` when no incumbent intent | `restart` when no incumbent intent | Compatible incumbent intent |
|---|---|---|---|---|
| `STARTING` | `COMPLETE/SUCCEEDED`, state `STARTING` | insert `STOP(target=current)`; return/join its retained outcome; transitions by the closed table | insert `RESTART(target=current)`; return/join its retained outcome; teardown before successor | same kind joins only on target-generation match; other kind `LIFECYCLE_CONFLICT` |
| `INITIALIZING` | `COMPLETE/SUCCEEDED`, state `INITIALIZING` | insert `STOP(target=current)`; return/join its retained outcome | insert `RESTART(target=current)`; return/join its retained outcome | same as `STARTING` |
| `READY` | `COMPLETE/SUCCEEDED`, state `READY` | insert `STOP(target=current)`; `DRAINING` with work, else `STOPPING` | insert `RESTART(target=current)`; `DRAINING` with work, else `STOPPING`, then one successor | same as `STARTING` |
| `DRAINING` | `COMPLETE/SUCCEEDED`, state `DRAINING` | no incumbent is an invariant violation because entry requires an intent; fail `SESSION_POISONED` without inserting a second intent | same | compatible incumbent joins; different kind `LIFECYCLE_CONFLICT` |
| `STOPPING` | `COMPLETE/SUCCEEDED`, state `STOPPING` | no incumbent is an invariant violation; fail `SESSION_POISONED` without inserting a second intent | same | compatible incumbent joins; different kind `LIFECYCLE_CONFLICT` |
| `STOPPED` | `COMPLETE/SUCCEEDED`, state `STOPPED` | `COMPLETE/NOOP/ALREADY_STOPPED`; no intent inserted | insert `RESTART(target=retained predecessor)`; allocate successor only after the already-established death/reap guard | compatible `RESTART` joins; compatible retained `STOP` returns its result; other kind conflicts |
| `CRASHED` | `COMPLETE/SUCCEEDED`, state `CRASHED`, with reap status | unreaped: insert/join `STOP(target=current)` to finish teardown; reaped: `COMPLETE/NOOP/ALREADY_STOPPED` while preserving `CRASHED` | unreaped: `SESSION_REAP_INCOMPLETE`, no successor and no new intent; reaped: insert `RESTART(target=retained predecessor)` | compatible intent joins; mismatch is stale; other kind conflicts |
| `POISONED` | `COMPLETE/SUCCEEDED`, state `POISONED`, with reap status | unreaped: insert/join `STOP(target=current)` to finish teardown; reaped: `COMPLETE/NOOP/ALREADY_STOPPED` while preserving `POISONED` | unreaped: `SESSION_REAP_INCOMPLETE`, no successor and no new intent; reaped: insert `RESTART(target=retained predecessor)` | compatible intent joins; mismatch is stale; other kind conflicts |

An inserted lifecycle intent continues independently and, when manager execution remains uninterrupted through response, returns its one retained terminal outcome. Stop success returns the resulting public state (`STOPPED`, or the preserved reaped `CRASHED`/`POISONED` diagnosis for terminal no-op); restart success returns `READY` and the immutable successor generation. Startup, teardown, crash, poison, cancellation, timeout, and reap errors use the closed outcome matrix below. `status` observes the retained state, generation, reap guard, and intent summary at one event and never inserts, joins, detaches, updates last use, or otherwise mutates session or caller state.

List entries expose only bounded lifecycle fields and never request/session routing provenance. Ordering is ascending by `(state_rank,last_use_manager_event_seq,creation_manager_event_seq,session_id_bytes)` with the fixed state rank `STARTING`, `INITIALIZING`, `READY`, `DRAINING`, `STOPPING`, `STOPPED`, `CRASHED`, `POISONED`. Filtering precedes ordering; a cursor resumes strictly after its encoded last tuple in the retained snapshot; `next` is present iff more matching entries remain. Identical snapshot/filter/limit inputs produce byte-identical pages. Capability metadata states `selector_publication_supported`, inline byte limit, and list-page maximum; it discloses no selector, root, or path. A session's last-use event is the admission `manager_event_seq` of a live traversal selected to that session, including an admission that later fails after selection; lifecycle inspection/control and list do not update last use.

`STOPPED`, fully reaped `CRASHED`, and fully reaped `POISONED` records remain retained and listable until retention expiry or capacity eviction. `EVICT` is manager-internal; public `stop` or `restart` against its nonterminal victim returns `LIFECYCLE_CONFLICT`, while `status` reports the victim's projected public state plus current nonterminal `EVICT` intent summary and any separate bounded terminal history. `max_sessions` is any configured positive integer. At each capacity admission decision, ordered by immutable admission `manager_event_seq`, the manager first assigns an existing unreserved free slot when one exists. Otherwise that blocked admission may own or join at most one nonterminal victim eviction at a time. New owners reserve distinct eligible victims in deterministic priority order: no-work terminal records by oldest `(terminal_manager_event_seq,session_id_bytes)`, then no-work `READY` sessions by oldest `(last_use_manager_event_seq,creation_manager_event_seq,session_id_bytes)`. A join is permitted only when the admission is waiting on that same already-reserved victim; it does not reserve another victim. Starting, initializing, draining, stopping, queued, active, already-reserved, or retained failed-`EVICT` sessions are ineligible absent explicit forced-shutdown policy. Slot assignments and victim reservations are one-to-one and manager-atomic: concurrent decisions never oversubscribe `max_sessions`, reserve one victim twice, reserve more victims than blocked admissions can consume, or let one admission own/join multiple victims. Thus multiple free slots may admit the same number of earliest legal contenders, and multiple blocked admissions may concurrently reserve distinct victims, while `max_sessions=1` remains the required single-slot fixture.

Successful `EVICT` freezes `COMPLETE/SUCCEEDED`, removes the victim session record (including its retained intent history), converts that victim's reservation into exactly one free slot, and only then wakes waiting admissions to re-evaluate in ascending admission `manager_event_seq`; because manager sequence values are unique, `manager_request_id` bytes are the final deterministic tie-break only for malformed/replayed fixture input that duplicates a sequence. The earliest legal contender takes each available slot; later contenders repeat the same free-slot-or-distinct-victim decision and return `RESOURCE_EXHAUSTED` only when neither is available. A terminal victim record with no process or contained survivors requires no teardown: successful eviction removes it and releases exactly one slot at the eviction manager event.

Failed `EVICT` freezes and returns the exact first-applicable retained result selected by the teardown table, retains the diagnostic session record and bounded terminal `EVICT` history, clears its victim reservation without releasing a slot, starts no replacement, and returns that same retained failure to every still-attached joined capacity caller; their own earlier deadline or cancellation still wins only for that caller. A record with retained failed-`EVICT` history is excluded from automatic capacity-victim selection and automatic eviction retry. A later explicit public lifecycle operation selected by the existing status/stop/restart table is a new intent, so terminal failed-`EVICT` history does not block it. Explicit cleanup succeeds only when the applicable lifecycle intent establishes process death, zero contained survivors, completed bounded stderr drain, and successful reap (or establishes that no child/process exists); it then leaves the table-selected public diagnosis/result, clears the failed-eviction quarantine, and either makes the safely reaped record ordinarily retention/eviction-eligible or removes it when the selected public semantics require removal, while preserving bounded diagnostic and terminal-history summaries until ordinary bounded-history or record-retention rules remove them. Retention expiry may remove the quarantined record only when process/containment safety proves that no live or unreaped contained process can remain and no capacity caller is attached. Expiry of an unreaped or otherwise unsafe record never silently removes it, clears its diagnosis, retries eviction, or releases capacity. Admissions instead choose another eligible victim or return `RESOURCE_EXHAUSTED`. `SESSION_REAP_INCOMPLETE` is selected only for terminate/kill failure or death-observation timeout, contained-survivor cleanup failure, or reap failure after observed death. Shutdown-protocol, unsafe exit/stdin/pipe I/O, and stderr-drain failures retain `SESSION_POISONED`; any future versioned teardown row likewise retains its own exact result rather than being remapped. No failed eviction is remapped to `RESOURCE_EXHAUSTED` or `SESSION_REAP_INCOMPLETE`; these are the sole tie-breakers and recovery rules.

## Crash, poisoning, and restart semantics

A language-server crash fails active requests with structured lifecycle diagnostics only when its ordered observation is the first applicable conversion before that request's terminal finalization. No active request is silently replayed against a replacement process.

A generation is `POISONED` and cannot receive queued or new work after any of these conditions:

- malformed or framing-corrupt stdout;
- an unknown or duplicate response ID;
- a canceled or timed-out request whose response state cannot be consumed unambiguously;
- initialization, synchronization, stdin write, or transport failure that makes protocol state unsafe or uncertain;
- shutdown-protocol violation;
- process death after an already-ordered poison predicate (which preserves the poison diagnosis);
- any manager invariant that permits multiple terminal reservations or installations, or prevents exactly one operation-local terminal installation on a surviving-manager finalization path.

Late responses that can be identified unambiguously are consumed and discarded without reopening their completed request. If identification or stream synchronization is uncertain, the generation is poisoned. Poisoning rejects queued work with `SESSION_POISONED`, begins bounded teardown, and requires a new generation before dispatch resumes.

For each active request, post-reservation conversion is decided by the first applicable ordered event by `event_seq` before terminal finalization. Unexpected observed child death converts `OPEN` or any unfinalized `RESERVED_RESPONSE`, `RESERVED_CANCEL`, or `RESERVED_TIMEOUT` to the single terminal `DOMAIN_ERROR/FAILED/SESSION_CRASHED`, preserves session state `CRASHED`, forbids `content`, `publication_receipt`, any publication attempt, and any success claim, and discards any selected interruption snapshot except for bounded digest/length metadata already available under the existing crash ceiling. An earlier poison predicate instead converts the unfinalized request to `DOMAIN_ERROR/FAILED/SESSION_POISONED` and preserves `POISONED`; later death is lifecycle evidence and cannot overwrite it. Generation invalidation or lease invalidation ordered before crash or poison may convert to `STALE_GENERATION` or `STALE_DOCUMENT_LEASE` respectively only when it is the first applicable ordered conversion. Conversion retains exactly one reservation owner, does not reopen arbitration or allow another contender, and permits at most one terminal-record append; surviving-manager finalization appends exactly one.

The operation-local `PUBLISHING` CAS is the cutoff: after it, later crash, poison, cancellation, timeout, generation or lease invalidation, and session lifecycle events affect session state and bookkeeping only and cannot change that operation outcome. A publication failure selected under target coordination therefore remains `PUBLICATION_ERROR/PUBLICATION_FAILED`. Conversely, crash observed before the `PUBLISHING` CAS converts the request and forbids the publication attempt. An in-process committed publication success is terminal once the operation-local arbiter installs the prebuilt in-memory success record; after a manager crash between rename and that installation or protocol delivery, no externally observable terminal MCP outcome—meaning an outcome delivered through the v1 protocol, not target-file existence—may exist. MCP v1 cannot determine success afterward through protocol state and emits no later synthesized or recovered envelope or outcome, performs no overwrite, deletion, or republication, and makes no recovery claim or cross-process recovery.

A later unpinned live request targeting `STOPPED`, `CRASHED`, or fully reaped `POISONED` may restart only by inserting or joining the exact typed `RESTART` intent defined above; lazy live admission and explicit `lsp_session_v1_restart` share that one intent implementation and retained result, but an explicitly generation-pinned live request never initiates or joins restart. The unpinned initiator and later unpinned joiners provisionally attach to that exact intent, not to its predecessor generation and not to a generic future-restart condition, with independent caller arbiters and immutable deadlines. An incumbent `STOP` or `EVICT` conflicts and each live caller fails `LIFECYCLE_CONFLICT`; restart startup/spawn/pipe/initialization failure maps to its exact closed startup code below and terminalizes every still-attached live caller with that same failure, while caller timeout or cancellation atomically detaches only that caller and maps to `REQUEST_TIMEOUT` or the applicable cancellation code without stopping the intent.

Only after predecessor death and successful reap, successor allocation, initialization, and that exact intent's transition to `READY`, the session serializer assigns one `restart_bind_event_seq` and atomically binds every still-attached unpinned live request on that intent to that intent's immutable `successor_generation`. In the same critical section, before any enqueue, it revalidates each request's immutable session-key bytes, deadline, `READY` state, intent attachment, and open caller arbiter; key mismatch returns `SESSION_KEY_CHANGED`, expiration returns `REQUEST_TIMEOUT`, and lost attachment or caller terminalization cannot enqueue. Timed-out or canceled attachments are absent from the bind set. A conflicting or later `RESTART` intent cannot capture an attachment from this intent, including after this intent fails. Only requests that pass all checks queue. All later provenance, request identity, generation checks, leases, dispatch, response acceptance, artifact publication, and terminalization use the final bound successor generation. Explicit lifecycle restart returns the same retained intent success or failure.

Crash, poison, restart, and initialization diagnostics remain visible. A successful later generation does not rewrite or upgrade evidence produced by an earlier failed generation.

Configuration or key changes create a distinct session rather than mutating a live session in place.

## Document synchronization

The session manager tracks documents opened through LSP Trace requests and the exact content identity last sent to the server.

Open-document state is generation-local and keyed by canonical document URI plus language ID. Every managed document has a monotonically increasing positive integer version within the generation; its first `didOpen` uses version 1 and every content-changing `didChange` increments by exactly one. Restart invalidates all leases and discards all open-document state after process death and reap.

At admission, a request captures only provisional source identities for its directly supplied seed and synchronized inputs: canonical URI/language identity plus the then-observed digest. Admission performs no `didOpen`, `didChange`, open-document mutation, version allocation, or lease acquisition. The queued record owns no document lease or LSP request ID.

Only when the request reaches queue head, after all prior active work is terminal and its lease-release/late-response bookkeeping is complete, the manager resolves and reads those direct inputs again under existing workspace rules, compares them with the provisional identities, and acquires generation-local leases in canonical URI order. A lease records `(session_id, generation, manager_request_id, URI, language_id, version, digest)`. Under session serialization, acquisition commits `didOpen` when absent or full-content `didChange` when the digest differs; an unchanged digest reuses the version. A provisional mismatch fails with `STALE_DOCUMENT_LEASE` before dispatch and commits no synchronization from the stale admission capture. Immediately before dispatch, response reservation, and the live operation's final publication-eligibility CAS, the manager revalidates each lease's generation, version, digest, and owner; failure terminalizes with `STALE_DOCUMENT_LEASE` and, when stream state is uncertain, poisons the generation.

The pre-dispatch lease set is limited to documents whose content LSP Trace directly reads or synchronizes for the request; it does not and cannot cover every file the language server may observe through indexing, configuration, imports, or watchers. If traversal discovers another document and LSP Trace must read or synchronize its content, it pauses traversal before that read, canonicalizes every identity currently known in that discovered acquisition batch, rejects duplicate conflicting identities, and sorts the batch by canonical URI bytes (then language ID bytes). Under v1's single active request stream, discovered batches are serialized by the session serializer and appended to that request's held lease sequence; no later batch is interleaved. The active request must not release or reacquire a lease to repair ordering. It acquires or revalidates the whole sorted batch atomically with respect to lease ownership, then performs required `didOpen`/`didChange` writes before consuming content or issuing dependent traversal. Existing held leases and every newly acquired or reused lease are revalidated under the same serialization immediately before the batch commits; failed revalidation terminalizes without a partial batch commit. Canonical ordering is required within each acquisition batch, not retroactively across already committed batches. Because v1 admits only one active request stream and queue-head acquisition waits for its terminal lease bookkeeping, no other active request can hold leases while waiting on this request, so no cross-request lease-order cycle can form. Discovery reported solely by the server, without an LSP Trace content read or synchronization, creates no lease and no direct-observation claim.

Queue cancellation, timeout, stop, crash, or poison removes queued work without lease release because queued work owns none. Active work releases ownership only after its terminal arbiter is finalized and any identifiable late-response obligation is recorded. A document remains open while any active request owns a lease. When the last owner releases and closure is elected, all close candidates are sorted by canonical URI bytes then language-ID bytes, assigned consecutive `event_seq` values, and complete `didClose` frames are written in that order before document state deletion; the owning versioned Stage 3 synchronization scenario specification must define the deterministic closure-election inputs, decision rule, and fixtures for retain-versus-close outcomes; no later work may acquire an entry between close decision and write. Delete, rename, language-identity change, generation invalidation, and explicit closure follow the same last-owner rule. `didClose` write failure poisons the generation. Generation teardown invalidates all leases before request terminalization and does not send `didClose` after transport shutdown has begun.

V1 requires a server synchronization capability compatible with full-content changes. Incremental-only or unsupported synchronization fails closed with `UNSUPPORTED_TEXT_SYNC`. Write or synchronization failure poisons the generation.

The manager must not assume that filesystem watchers delivered a change. Documents not directly read or synchronized by LSP Trace remain outside the direct-observation claim.

A server that requires broader project synchronization may observe additional workspace state, but that observation is server-reported and unauthenticated.

## Concurrency policy

V1 defaults to one active LSP request stream per session.

Different sessions may run concurrently within global resource limits. Requests targeting one session are queued deterministically unless the selected server profile explicitly opts into a later qualified concurrency mode.

Initialization, shutdown, restart, document synchronization, and request dispatch are serialized per session. Lifecycle stop or restart rejects new work and waits for or cancels active work according to an explicit bounded policy.

No concurrency claim is inferred from an LSP server's advertised capabilities alone.

## Cancellation, timeout, and progress

V1 emits no MCP progress notifications. Adding progress tokens or notifications requires a later compatibility decision.

Each accepted MCP call receives one manager request ID and produces at most one externally observable terminal MCP outcome, meaning an outcome delivered through the v1 protocol and excluding target-file existence; uninterrupted manager execution through finalization and protocol delivery produces exactly one. The deliberate v1 exception is manager death after successful atomic rename but before terminal-record append or response: it may produce no externally observable outcome, and MCP v1 cannot determine success afterward through protocol state or synthesize or recover an outcome. On request receipt, before admission or capacity decisions and before acquiring any session mutex, capacity semaphore, queue slot, or startup/reap barrier, the manager allocates the request's immutable `admission_manager_event_seq`, then reads the monotonic clock once as `received_at` and derives immutable `deadline = received_at + request_timeout`. Admission records both values unchanged. Lock, capacity, queue, barrier, lease, synchronization, and dispatch waits consume that budget; no phase resets or extends it. Deadline expiration obtains the next session `event_seq` and competes through the same terminal-arbiter CAS as cancellation. If expiration wins before dispatch, queue ownership is removed, no LSP ID is allocated, no cancel traffic is sent, and no artifact is delivered. If it wins after dispatch while `OPEN`, it enters `RESERVED_TIMEOUT`, selects the eligible snapshot or none, and sends best-effort `$/cancelRequest` for every unresolved owned LSP ID in ordinal order. If any typed reservation already owns the arbiter, timeout loses as too late. Cancellation of queued work removes it from the queue without LSP traffic and returns `CANCELLED_BEFORE_DISPATCH`. Cancellation after dispatch enters `RESERVED_CANCEL`, cancels traversal context, and sends best-effort cancellation for every unresolved owned ID in ordinal order. Concurrent LSP responses remain intermediate events or are consumed against tombstones after interruption; they never produce a second outcome.

Request timeout follows the same race and post-request safety rules as cancellation and returns `REQUEST_TIMEOUT`. Late identifiable responses are discarded. An unknown/ambiguous response identity or uncertain stream state poisons the generation before later work can dispatch. A cancel write failure is recorded as `WRITE_FAILED`; it poisons only when the failed write makes framing or stream state uncertain, while a known zero-byte/rejected-before-write failure remains diagnosable without conflating cancellation state with response state.

Cancellation does not stop a healthy shared session by default. It stops or restarts the generation only when the poison predicate holds, the process exits, or explicit lifecycle policy requires restart.

During traversal while the manager arbiter is `OPEN`, request-owned traversal code may commit an immutable schema-valid partial snapshot without terminal reservation. Commit validates and freezes exact artifact bytes, schema identity, digest, byte length, incompleteness diagnostics, generation, and lease identities, then assigns one `event_seq`; a later snapshot is a distinct value. A winning cancel/timeout reservation atomically selects only the latest strictly earlier commit, subject to command eligibility and final generation/lease revalidation. An at-or-after snapshot and mutable builder state are ineligible. Inline selected bytes are part of that interruption terminalization. Selector delivery is owned by `RESERVED_CANCEL`/`RESERVED_TIMEOUT`, never `RESERVED_RESPONSE`; publication succeeds before interruption finalization, and failure converts to `PUBLICATION_ERROR/PUBLICATION_FAILED`. No selected snapshot means no artifact fields and no publication attempt.

Canceled `slice` and `incoming` operations preserve their existing command-specific structured-evidence distinctions when an eligible committed partial snapshot exists. MCP cancellation metadata is transport state and does not replace graph status.

## Stderr handling

Each persistent process has one continuously drained stderr stream with fixed byte, event-count, and `stderr_retention_duration` budgets. Retention eviction is oldest-first by `(arrival_monotonic_time, stderr_sequence)`; duration expiry is applied first, then oldest events are evicted until both count and byte budgets hold.

At stderr-byte acceptance under the session serializer, the manager snapshots the ordered active manager-request ID set and assigns the stderr sequence and `event_seq`; this is the sole active-ID capture linearization point. The manager records monotonically ordered stderr events containing session ID/generation, sequence, arrival time, that captured active-ID set, bounded text, and cumulative generation-local counters `total_events_seen` and `total_bytes_seen`. Eviction tombstone accounting derives dropped counts by counter subtraction, so repeated windows remain cumulative and deterministic. If counter state is corrupt, overflowed, or unavailable after recovery, the marker sets `accounting:"unavailable"`, omits numeric dropped counts, retains the bounded reason and first-retained sequence, and never estimates; this bounded state poisons only when stream safety is also uncertain.

Correlation to a request is temporal and tool-derived. It is not proof that the request caused the stderr event. Events with no active request remain session-global lifecycle diagnostics.

A request artifact may retain only its bounded correlated window plus explicit truncation metadata. The server-wide raw stderr history is never copied wholesale into every artifact. Any duration/count/byte eviction intersecting the requested window inserts exactly one structured marker at the beginning of retained events: `{"type":"stderr_truncated","version":1,"reason":["duration"|"event_count"|"bytes",...],"dropped_events":<uint64>,"dropped_bytes":<uint64>,"first_retained_sequence":<uint64|null>}`. `reason` contains the applicable enum values in the fixed order shown, counts cover only events omitted from that window, and `first_retained_sequence` is null when none remain. The marker consumes the artifact diagnostic budget but not the process stderr budget. Eviction is oldest-first and never silently drops the boundary.

## Resource limits

The MCP server enforces configurable bounds for:

- maximum live sessions;
- maximum queued requests per session;
- global concurrent requests;
- session idle timeout;
- initialization timeout;
- request timeout;
- shutdown timeout;
- stderr bytes and event count;
- inline MCP result bytes;
- published artifact storage according to existing policy.

Eviction follows the deterministic lifecycle ordering above and never targets a session with active work unless forced shutdown policy applies. Resource exhaustion fails closed with structured diagnostics.

Every live generation runs inside the independently enforced managed process containment boundary attested by the process-lifetime `VERIFIED` probe result consumed before capability publication. The attestation covers supported primitive/profile identity, bounded owner-death cleanup independent of manager teardown, every descendant, non-escape/transfer/reparent/delegation under all admissible granted authority, and absence of forbidden containment-control authority. Any unsupported, indeterminate, failed, mutable, or incomplete check instead produces `UNAVAILABLE(reason, failed_check)` and immutable `CONTAINMENT_UNAVAILABLE`; valid calls return `DOMAIN_ERROR/FAILED/PROCESS_CONTAINMENT_UNAVAILABLE` without provenance, session/server selection, or execution. The bounded internal result is non-authoritative and exposes no sensitive credentials or paths. Runtime teardown still has explicit graceful, terminate, kill, death-observation, survivor, stderr-drain, and reap deadlines. Exact OS enumeration, evidence, primitive mechanics, timing, and probe fixtures are Stage 2-owned. The manager claims no control only over genuinely unrelated or pre-existing processes that never descended from the managed generation; an escaped or transferred descendant is a failed probe/check, not a scope exclusion.

## Trust and isolation

Language-server profiles execute binaries with the MCP server's operating-system permissions. Existing trusted-server and trusted-workspace warnings remain binding.

V1 is single-user and process-local. Sessions are never shared across operating-system users, MCP server processes, or distinct configured trust domains.

The session key includes trust-domain identity so future embedding cannot accidentally pool sessions across callers. Defining or authenticating trust domains is external to LSP Trace in v1.

Profile environment entries remain references. Raw environment values are resolved only at execution and excluded from MCP responses, session listings, logs, and graph invocation fields according to existing projection rules.

MCP clients must not be permitted to choose arbitrary server commands unless the host explicitly grants that capability. Named profiles are the default allow-list boundary.

## Evidence and authority composition

MCP operations preserve existing evidence classes, support contributions, claim ceilings, completeness boundaries, and custody semantics.

The MCP operation envelope, not any stable graph schema, carries routing provenance in this required versioned object only for exact-selector lifecycle results that resolved a retained session and live operation results admitted to a session, including post-selection errors:

```json
{
  "provenance": {
    "version": "1",
    "mcp_session_id": "opaque-process-local-id",
    "mcp_session_generation": 1,
    "mcp_session_key_digest": "sha256:...",
    "mcp_request_id": "generation-bound-manager-request-id",
    "session_reused": false
  }
}
```

Offline operations and errors produced before session selection omit `provenance`. Once required, the object and all five members are present; `mcp_request_id` equals envelope `request_id`, and the session/generation values equal the terminal arbiter record. `session_reused` is a routing fact with these exact semantics: for live admission it is `true` iff the selected session and current generation were already allocated before that admission (including queued, joined, and later post-selection stale-generation/domain-error outcomes), and `false` iff that admission allocated the session or generation; for `status`, `stop`, and `restart` it is `true` whenever selection resolves to a retained session, including joined operations, idempotent/no-op stop, and stale-generation or other errors after selection. A successful restart that allocates a new generation still reports `true` because it selected the retained session. Pre-selection schema errors, `SESSION_NOT_FOUND`, list results, and disabled-live errors omit provenance and therefore have no `session_reused` value. The object version governs its member meanings independently of graph schemas. These fields establish process/session routing provenance only. They contribute zero evidentiary support and do not authenticate the server, workspace, source, execution, user, or producer.

Multiple artifacts from one session or generation are not independent observations merely because they came from separate MCP requests. Session reuse may correlate cache state, indexing state, hidden inputs, stderr, and server defects.

MCP transport success, session health, reuse, or restart does not upgrade native evidence authority or selector custody.

## Structured errors and status

The independently versioned MCP operation envelope has this closed base field set: required `envelope_version`, `envelope_schema_id`, `tool`, `request_id`, `outcome`, `operation_status`, and `isError`; conditional `code`, `diagnostics`, `provenance`, `result`, `content`, `publication_receipt`, `artifact_schema_id`, `artifact_digest`, `artifact_byte_length`, and `retained_failure_metadata`. No other base field is permitted. Variant requiredness, nullability, and mutual exclusion remain defined by the exhaustive matrix and committed stage schemas rather than by the base set alone. `envelope_schema_id` identifies one schema for that complete operation-envelope variant and must appear in the canonical tool's `envelope_schema_ids` for the current process and availability; the tool's MCP `outputSchema` is the closed discriminated union of exactly those complete-envelope schemas, and validates the entire object selected by its required `envelope_schema_id`, not merely envelope `result`, inline artifact `content`, or another projection.

Under the MCP protocol version selected by the Stage 1 manifest, every handled tool operation whose manager execution remains uninterrupted through response returns exactly one MCP `CallToolResult`; every accepted operation returns at most one, and the post-rename/pre-terminal manager-death boundary may return none. Its `structuredContent` is exactly the complete operation envelope object, with no wrapper or omitted envelope fields. The outer `CallToolResult.isError` is present and equals envelope `isError`. Outer MCP `content` is the empty array required by that MCP version when no content blocks are supplied; it never contains a text, JSON, resource, or other duplicate/mirror of the envelope. If a later MCP version permits omission rather than an empty array, adopting omission requires a separately accepted transport-contract update; v1 goldens use the empty array. Envelope `content` is not outer MCP `content`: it is the nested inline artifact delivery field, and its exact JSON representation and byte encoding remain owned by the applicable stage artifact/envelope schema. MCP protocol, input-schema, and unknown-tool errors occur before operation-envelope construction, return through normal MCP error behavior, and contain no operation envelope; adapters must not invent one for those failures.

### Committed schema and transcript contract

Contracts are incremental. Before Stage 1, the manifest pins one immutable exact MCP protocol revision and publication date, and the repository commits schemas, manifest entries, and success/failure transcripts for the six canonical offline tools (including `lsp_trace_v1_capabilities`), all envelope variants they can produce, and reserved disabled-call input schemas for all four canonical lifecycle and both canonical live names. Stage 1 goldens enumerate the exact native MCP/JSON-RPC error forms and precedence for protocol, input-schema, and unknown-tool failures before envelope construction; none contains an operation envelope. The manifest has one entry per canonical name, records its ordered `aliases` array, maps canonical and alias dispatch to the same input schema and envelope variants, counts only canonical entries, and requires envelope `tool` to be canonical for either spelling. Before Stage 2 it adds lifecycle envelope variants and transcripts; before Stage 3 it adds live variants, transcripts, and the versioned `provenance` object cases not already required by lifecycle. Each golden is exact newline-delimited MCP JSON-RPC fixture framing: one normalized JSON object per UTF-8 line, LF terminator, no BOM, object keys sorted by UTF-8 bytes, array order preserved, integers in shortest decimal form, and no insignificant whitespace. This canonical serialization is solely fixture normalization and does not restrict semantically equivalent protocol-valid peer JSON whitespace, object-key order, or framing permitted by MCP. The replacement manifest is itself canonical JSON and lists every replaced nondeterministic JSON Pointer, its typed fixture value, and justification; replacement occurs before canonical serialization, undeclared replacement fails, and transport request IDs remain transport-owned. The normative manifest names every reserved tool and maps it to one input schema and all envelope variants permitted for each accepted binary and availability. It and capability metadata declare every schema identity with exactly one immutable versioned schema family and exactly one layer, `envelope` or `artifact`. `envelope_schema_id` names only an envelope-layer schema for the complete operation envelope. `artifact_schema_id` names only the artifact-layer schema of the exact delivered artifact bytes or inline content when that artifact family has a schema; it never names an envelope, receipt, diagnostic, or graph wrapper, and it does not replace or reinterpret an artifact's existing internal graph `schema_version`. URI grammar, registry resolution, and registry implementation remain stage-owned. The schema registry and manifest own overlap detection and must prove that every emitted envelope validates against exactly the schema named by its required `envelope_schema_id` and against no competing envelope variant; exact registry and proof mechanics remain owned by the applicable stage specification. Coverage includes all offline tools, all lifecycle tools, both live tools, inline complete/incomplete content, permitted cancellation and timeout partial content, publication receipt, domain error, cancellation, timeout, publication error, idempotent/no-op lifecycle success, stale generation, disabled-live behavior, and every required/forbidden provenance case. The fixture catalog includes byte-stable ordered races for crash after each typed reservation but before the `PUBLISHING` CAS, poison-before-death, generation- and lease-invalidation-before-crash, publication-failure-before-crash, crash-before-publication eligibility, in-process publication rename/success non-interleavability, crash after rename before terminal installation or response, pre-ticket receipt/envelope construction failure, crash after the `PUBLISHING` cutoff, and cross-session/offline/live lock inversion and deadlock attempts. The post-rename/pre-terminal fixture proves the caller target may exist without a process-local in-memory terminal record or externally observable terminal MCP outcome, where that outcome means one delivered through the v1 protocol and excludes target-file existence; the in-memory candidate success receipt has no evidentiary meaning or success claim. MCP v1 cannot determine success afterward through protocol state and emits no later synthesized or recovered envelope or outcome, performs no overwrite, deletion, or republication, makes no recovery claim, and exposes no recovery tool or input variant. V1 provides no cross-process recovery; durable terminal storage and any cross-process recovery/reporting fixture belong only to a separately accepted stage or later versioned surface. Each ledger proves the first applicable `event_seq`, unchanged single reservation ownership, exact terminal-record presence or crash-boundary absence, exact lifecycle state/code when one is emitted, and required artifact-field prohibition. A schema or golden omitted from the manifest is not a v1 contract.

The MCP protocol request ID is transport-owned and is not copied into the operation envelope. Envelope `request_id` is the generation-bound manager request ID; goldens prove distinct manager IDs and, when LSP requests are dispatched, the ordered bounded `lsp_requests` summary and complete fixture ledger agree with the same session/generation ownership relation. A singular `lsp_request_id` field is forbidden. `operation_status` describes domain execution (`SUCCEEDED`, `INCOMPLETE`, `FAILED`, `CANCELLED`, `TIMED_OUT`, or `NOOP`); `outcome` selects the envelope variant (`COMPLETE`, `INCOMPLETE`, `DOMAIN_ERROR`, `CANCELLED`, `TIMED_OUT`, or `PUBLICATION_ERROR`). `code` is required for every non-`COMPLETE` outcome and forbidden for successful `COMPLETE` except `NOOP`, where it is `ALREADY_STOPPED`. `TIMED_OUT` requires `operation_status: TIMED_OUT`, `isError: true`, and `code: REQUEST_TIMEOUT`. Graph status remains inside graph content and is not inferred from these fields.

For every successful `ENVELOPE_RESULT` variant, including `COMPLETE/NOOP/ALREADY_STOPPED`, `result` is required and non-null. It is forbidden for every `ARTIFACT_DELIVERY`, error, cancellation, timeout, incomplete, and publication-error variant. `result` is mutually exclusive with envelope `content`, `publication_receipt`, `artifact_schema_id`, `artifact_digest`, `artifact_byte_length`, and `retained_failure_metadata`. Failures never preserve a partial or diagnostic value in `result`; bounded failure information remains only in `diagnostics` and the already-defined retained-failure fields. Every successful `COMPLETE` or `NOOP` row is therefore exactly non-null `ENVELOPE_RESULT` or `ARTIFACT_DELIVERY`; no stage schema may define a successful no-result variant.

Partial `content` is permitted for `INCOMPLETE`, and for `CANCELLED` or `TIMED_OUT` only when dispatch occurred and traversal committed an immutable, schema-valid partial snapshot at a snapshot-commit `event_seq` strictly before the terminal contender's winning `event_seq`. Such content carries the same artifact identity and validation guarantees as complete content plus explicit incompleteness diagnostics. Admission, pre-dispatch cancellation, and pre-dispatch timeout contain no partial artifact. Exactly one of `content` or `publication_receipt` is required for an artifact-bearing terminal variant (`COMPLETE`, `INCOMPLETE`, or an eligible delivered partial `CANCELLED`/`TIMED_OUT`); both are forbidden when no artifact is delivered. For inline delivery, `content` is required and `publication_receipt` forbidden; for selector publication, `publication_receipt` is required and `content` forbidden. `artifact_schema_id` is required with either delivery field exactly when the delivered artifact family has a declared artifact-layer schema, and is forbidden when it does not; the receipt's schema identity, when present, must equal it. No-artifact outcomes forbid `artifact_schema_id` except the two digest-only cases below.

`PUBLICATION_ERROR` always forbids `content` and `publication_receipt`; it requires `artifact_digest`, `artifact_byte_length`, and `retained_failure_metadata` for the exact intended artifact bytes, and requires `artifact_schema_id` exactly when those intended bytes belong to a declared artifact schema family. `SESSION_CRASHED` likewise forbids both delivery fields and publication; it permits digest-only `artifact_digest`, `artifact_byte_length`, and, exactly when applicable to those already-available immutable bytes, `artifact_schema_id`, but only as a complete trio, and otherwise forbids all three. Every other no-artifact outcome forbids all artifact identity, digest, length, content, and receipt fields. Publication retained-failure metadata remains bounded to failure stage, stable code, cleanup status, atomic-rename status, and truncation indicator and must not expose the selector or a server-chosen path.

Envelope v1 has closed field and enum sets. Stage 1 MCP server capability metadata is returned only by the closed, always-advertised `lsp_trace_v1_capabilities` tool (or its unadvertised `lsp_trace_capabilities` alias) defined above; MCP initialization metadata is not relied upon. A request selects exactly one advertised envelope version through the canonical tool name patterns `lsp_trace_v<version>_*` and `lsp_session_v<version>_*`; unversioned names in this ADR alias v1 only and must not silently negotiate another version. Unsupported versioned names are unknown tools. Clients may ignore unknown fields only from a later declared envelope version or explicitly versioned schema family; v1 schemas reject them. Required fields, meanings, request-ID relations, outcome/status/code combinations, tool names, provenance rules, digest scope, and existing v1 schema-ID meanings cannot change. A schema ID accepted into the global v1 registry is immutable and is never rebound, repurposed, or removed from a compatible accepted v1 manifest/binary lineage. That global identity-retention rule is distinct from a process's availability-specific current permitted subset: capability metadata advertises only that process's exhaustive current subset. A later accepted manifest and new process may append a newly committed, explicitly versioned schema ID without making it applicable to an earlier process. Adding any error code, field, outcome, status, or tool-to-variant mapping requires envelope version 2 or a separately named/versioned schema family; there are no open additions under v1. Graph and existing CLI schema compatibility remain governed externally and are not adjudicated by this ADR.

### Reserved-name behavior across lifecycle/live availability

Canonical lifecycle/live names and their unversioned aliases remain reserved whenever the canonical names are omitted from `tools/list`. `lsp_trace_v1_capabilities` is never omitted or disabled, and its alias therefore never follows unavailable reserved-name dispatch. Dispatch precedence is fixed for either spelling: recognize and canonicalize the name against the immutable capability entry; validate arguments against that canonical tool's reserved input schema; inspect implementation availability; for an implemented persistent lifecycle/live entry inspect the process-lifetime containment result; then inspect runtime enablement. Thus malformed input to any unavailable canonical name or alias is the same MCP tool-validation error with no envelope. Valid input through either spelling yields `DOMAIN_ERROR/FAILED/TOOL_NOT_IMPLEMENTED` for `NOT_IMPLEMENTED`, `DOMAIN_ERROR/FAILED/PROCESS_CONTAINMENT_UNAVAILABLE` for `CONTAINMENT_UNAVAILABLE`, or `DOMAIN_ERROR/FAILED/LIVE_LSP_DISABLED` for `RUNTIME_DISABLED`, always with canonical envelope `tool`; `ENABLED` alone dispatches the handler. The containment-unavailable envelope has no provenance because no session/server is selected or started. These three codes are distinct closed v1 codes and cannot substitute for one another. A name absent from `tools/list` is merely unadvertised and still follows this reserved-name behavior when present in the authoritative capability reserved/canonical/alias registry. Only a name absent from that registry, including any unsupported versioned name, is an MCP unknown-tool error with no envelope. Goldens pair canonical and alias cases for malformed-unavailable, valid-not-implemented, valid-containment-unavailable, valid-runtime-disabled, enabled-valid, unknown-name, schema identity, envelope identity, and recognition/validation-before-implementation-before-containment-before-runtime precedence.

## Architecture/specification boundary

This ADR governs observable safety, authority, lifecycle, and compatibility invariants and the exact public contracts explicitly selected here, including canonical tool names, aliases, and advertisement, `lsp_trace_v1_capabilities`, `SessionKeySelectorV1`, envelope outcomes/codes, crash artifact prohibition, and public lifecycle projections. Versioned stage manifests, schemas, goldens, and scenario specifications govern exact wire-schema registry mechanics, fixture construction, event scripts, and conformance data needed to implement those invariants.

Absence or incompleteness of a required stage artifact blocks that stage's acceptance gate; it does not block acceptance of this architectural decision except where this ADR itself selects an exact public contract. The Stage 1 specification must name the JSON Schema dialect, stable schema `$id` rules, registry resolution rules, and all configuration-derived bounds reported by immutable capability metadata. The Stage 2 and Stage 3 specifications must own exact scenario grammar and ledger mechanics. In particular, the Stage 3 synchronization specification must define and golden-test deterministic `didClose` election; this ADR requires deterministic last-owner closure behavior but does not falsely claim the election mechanics are already complete.

## Internal architecture

Extract shared command operations behind typed Go APIs that accept explicit inputs and return structured results. The CLI and MCP adapters call those APIs.

The MCP server must not invoke the CLI through a shell or parse human-oriented stderr. It may reuse publication functions and schema validators through internal packages.

The session manager owns process startup, initialization, document synchronization, request serialization, cancellation, shutdown, restart, stderr draining, and eviction. Traversal and graph construction continue to use existing traversal logic.

## Compatibility

This decision does not change existing CLI syntax, graph schemas, inspection/filter schemas, selectors, receipts, exit codes, or authority claims.

Offline MCP results are projections of existing operations. Live MCP graph artifacts remain valid existing graph versions; MCP session-routing provenance is carried only by the versioned operation-envelope `provenance` object. Session fields must not be inserted into a stable graph schema without a separate compatibility decision.

The MCP operation envelope, tool names, input schemas, and lifecycle semantics form a new compatibility surface and require explicit versioning.

Named profile resolution remains identical between CLI and MCP. MCP does not add automatic profile selection. MCP v1 reserves the canonical offline, lifecycle, and live tool names and their exact unversioned aliases defined in this ADR; the runtime capability gate controls advertisement and execution of canonical lifecycle/live tools and alias dispatch without changing their shared contracts. Aliases are callable compatibility entries only: they are never advertised, never counted, never emitted in envelope `tool`, and never negotiate a future version.

## Rejected alternatives

### Replace the CLI with MCP

Rejected because scripts, CI, shell workflows, and offline evidence handling require a stable standalone interface.

### Shell out to the CLI from the MCP server

Rejected because stderr parsing, process nesting, cancellation, structured status, and persistent-session reuse would be brittle and lossy.

### Start with live sessions before offline tools

Rejected because offline tools establish MCP schemas, output limits, publication handling, and authority boundaries without arbitrary process execution.

### Share sessions by workspace path alone

Rejected because command, arguments, environment, language configuration, profile, and trust domain can materially change server behavior.

### Automatically choose a profile

Rejected because extension or language inference could silently execute an unintended binary or reuse an incompatible session.

### Replay canceled requests after restart

Rejected because hidden server state may differ and replay would blur request identity and provenance.

### Attach all session stderr to each artifact

Rejected because it duplicates sensitive unrelated data and falsely suggests request causation.

### Claim one workspace snapshot per persistent session

Rejected because files and hidden server state may change between requests and watchers are not a custody mechanism.

### Run one shared multi-user daemon

Rejected because authentication, authorization, process isolation, resource fairness, and cross-user leakage require a separate design.

## Consequences

### Positive

- Repeated investigations can reuse expensive indexing and initialization.
- Agents receive structured evidence tools without parsing CLI prose.
- Offline evidence operations can ship before arbitrary process execution.
- Session reuse remains explicit and mechanically isolated.
- Existing graph, custody, and authority contracts remain intact.

### Negative

- Persistent process lifecycle, synchronization, cancellation, and multi-slot deterministic eviction add substantial complexity; failed victims can intentionally reduce usable capacity until explicit safe cleanup or safe retention expiry.
- Workspace mutation and hidden server state limit reproducibility.
- Long-lived processes increase resource and sensitive-data exposure, and persistent lifecycle/live availability depends on a closed process-lifetime containment probe result; any unsupported, indeterminate, failed, mutable, or incomplete check makes availability immutable `CONTAINMENT_UNAVAILABLE`, while the exact OS evidence and mechanics remain Stage 2-owned.
- A new versioned MCP operation surface, including exact `CallToolResult.structuredContent` envelope binding, empty outer `content`, two exhaustive exclusive success output kinds, and process-current envelope/artifact capability identity sets, requires compatibility maintenance.
- Versioned MCP envelope provenance adds a compatibility surface while stable graph schemas remain unchanged.
- Same-process publication requires an operation-local atomic terminal/publication arbiter for every artifact-producing operation plus an identity-based process-local target-coordination domain with a universal outer lock order and release before session/lifecycle bookkeeping; the irrevocable pre-coordinator ticket simplifies target coordination to immutable identity checks and prebuilt terminal installation, but adds collision-identity, cutoff, and deadlock-proof obligations and intentionally provides no cross-process guarantee beyond atomic no-replace namespace visibility. V1 also intentionally makes no directory-entry crash-durability claim.

### Neutral

- MCP does not improve language-server correctness or completeness.
- Persistence does not authenticate source or execution.
- Repeated requests from one session are not independent evidence.
- CLI startup-per-invocation remains available.
