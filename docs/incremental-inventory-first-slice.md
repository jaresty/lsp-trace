# Incremental inventory: controlled first ownership slice

`applicationinventory.DurableStore` now owns pre-evidence creation, admission reservations, retained-evidence commits, sealing and the existing semantic task transitions. It is not a staging controller or parent of `scopejob`. All phases use the same `inventory-run-<RunID>.json` exact-predecessor CAS ledger. The temporary `--scope-job-candidate` now selects this owner for metadata enumeration; ordinary census routing is unchanged.

## API and phases

- `Create(ctx, OwnedInventoryConfig)` first commits a self-contained `Creating/CLAIMED` head with the full creation charge, embedded validated config and its exact future immutable-object reference. It then publishes config and CASes this same head to the selected workflow's `Collecting/READY` or `Enumerating/READY`, with no task or evidence. Cancellation before the first claim leaves no artifacts. After claim, failure retains charged uncertainty and returns a discoverable RunID alongside the error. `CREATION_UNCONFIRMED` means initial CAS/readback could not be established; inspect that RunID without retry/rebase/refund. Collision returns the existing owner's status without changing its charge.
- `JobStatus(ctx, run)` is bounded, uncharged, non-executing inspection. `JobExpiry` is `NONE`. Its `Head` is the expected predecessor for the next mutation. Repeated successful status reads are readback, not operation replay.
- `ReserveAdmission(ctx, run, expectedHead, InventoryAdmissionBinding)` claims and spends a configured slice before retention effects. The next zero-based index and expected request/source-unit IDs are bound in the head. Lead ID is `<RunID>-<six-digit-index>`, fixed before retention and independent of a future manifest hash.
- `Admit(ctx, reservation, PrivateSelectedResultV2)` consumes both the local one-shot operation and the existing opaque retention authority. DTOs only constrain identity; the unchanged admission/intent/unit/request guards remain authoritative. An immutable admission record links the prior record and genuine retained evidence reference. The head advances only on exact claimed-predecessor CAS.
- `Seal(ctx, run, expectedHead)` claims a finite slice, checks the bounded ordered record chain, materializes explicit PREPARED dispositions, and enters the existing Describe controller under the same run ID. All earlier Used/Work/Packets remain charged. Completion and successor delivery are protected before task issuance.
- Existing `Task`, `Read`, `Submit`, and `Result` then apply. No alternate judgment parser or publisher exists. The controlled integration test stops at the second Describe; it makes no publication-success claim.

For the supplied-admission workflow, `Creating/CLAIMED -> Collecting/READY` completes funded creation. Lost creation claims remain terminal partial uncertainty, even if config publication completed. `Collecting/READY -> Collecting/CLAIMED -> Collecting/READY` admits one item. `Collecting/READY -> Sealing/CLAIMED -> Describe/READY` seals. Subsequent phases remain Describe, GroupDecision, Reviewer, Published.

A claimed operation is `PARTIAL_UNCERTAIN` to a reopening observer. Only the already-running operation can still commit its exact predecessor. If lost, this slice has **no recovery transition**: Seal and new admission reservations refuse; spent work is never refunded and orphan bytes are not admitted. Do not poll or replay to resolve it. A failed Seal is likewise terminal partial uncertainty. This is deliberately conservative, not crash recovery by reacquisition.

## Formats and bounds

- New head: `lsp-trace.durable-inventory-head.v4` (explicit self-contained creation phase).
- Immutable config: `lsp-trace.inventory-owned-config.v2` with `MaxAdmittedEvidenceBytes`.
- Linked record: `lsp-trace.inventory-admission.v2` with `AdmittedEvidenceBytes`.
- Creation charge model: `lsp-trace.inventory-create-cost.v1`.
- Sealed semantic state: `lsp-trace.inventory-state.v2`.
- New task/contract: durable-inventory-task.v2 / census-task-contract.v2.
- Existing completion quote algorithm remains v2. Legacy Start/head v2/state v1/task v1 behavior and historical 180-second run / 120-second cumulative semantic limits remain unchanged; recognized v1 stored heads stay non-executable. The unreleased fixed-charge incremental head v3 is now explicitly recognized/refused, not migrated or re-costed. Its config v1 `RetainedBytes` field is not accepted as the new field or reinterpreted as a broader quota. Existing stored bytes/debits are never rewritten.

Configuration admits **1–16** items in this first slice, stricter than the existing semantic 100-prepared cap. There is no repository-scale or 225k-entry representation claim. Before Seal there is no growing whole-manifest copy: one bounded head, one immutable config, and one bounded immutable record per admission. Only `Creating` can use a 64 KiB head to hold the self-contained <=32 KiB canonical config; READY and later heads retain the 16 KiB bound. Seal alone creates the bounded existing semantic arrays. Existing immutable object bounds remain 8 MiB.

Logical work is at most 64 MiB; packets remain at most 64. Create spends `8*C + 32*(65536+16384) + 32768` logical bytes, where `C` is the actual canonical encoded config length (1–32768). Eight config traversals cover encoding/copy/hash/publication/readback; 32 traversals of each bounded head cover envelope/copy/hash/CAS verification and bounded failure/status readback. Fixed overhead covers IDs/descriptors/scalars. Arithmetic and the complete quote plus one admission and Seal are checked before effects. This is a conservative logical-work model, not measured RSS. Each admission permanently spends its configured 128 KiB–8 MiB slice. Seal spends 2 MiB. Inner work uses `NewReservedCallerBudgetV3` with prior spending, never a fresh run allowance. Unused reservations are not refunded. Status/config validation are administrative inspection, not execution grants. Unknown future admission count/content is not fully funded up front: Seal can refuse its inner budget or completion quote, leaving its claim spent and no issued task. Successor submission retains existing staged admission behavior.

The provisional default `MaxAdmittedEvidenceBytes=2 GiB` is a **post-retention acceptance limit**, not a pre-effect disk cap. It sums retained evidence-object bytes only for successfully committed admissions; config/records, semantic artifacts and orphan evidence are excluded. A rejected retention can therefore leave orphan bytes, while its operation's logical budget stays spent. **The user's 2 GiB total-retained-storage requirement is UNMET and deferred.** This narrower counter is not an owner-approved substitution for that requirement. No physical quota or cleanup mechanism is implemented here.

There is no overall job wall-clock deadline. Each admission/Seal operation has a configured lease of at most 30 seconds. Each semantic task has a fresh configured lease of at most 30 seconds, and `(MaxAdmissions+2)*TaskWindow <=120s`; cumulative semantic reservations still cannot exceed 120 seconds. New stored `RunDeadline=0` explicitly means NONE, not a renewed legacy deadline. Retention of an already-completed opaque result does not renew its original producer operation.

## Controlled evidence and deferred integration

Tagged tests use the fixed `sessionruntime.NewControlledDescribePipeFixture` io.Pipes/goroutine backend, with actual M/P/S ownership and explicit R `REFERENCED_SYMBOL` selection. No SELF executable, provider OS process, real acquisition, census scan, or retained-store lifecycle replay is used. Cleanup checks pipe join, physical close and zero sessions/workers. This establishes controlled custody mechanics, not native-provider qualification or process containment.

The interrupted-commit test replaces a claimed head with a different valid claimed predecessor before retention; genuine evidence is written, then admission CAS fails. Reopen confirms unchanged spending, zero admitted items, orphan evidence and refusal to Seal/replay. It is a deterministic stale-predecessor fault, **not an OS kill/power-loss test**.

## Bounded enumeration consolidation (independent parent review required)

The candidate CLI no longer invokes `scopejob.Start`. It calls `Create`, emits the inventory RunID receipt, then calls `Enumerate` on that same owner. `census job-status <64-lowercase-hex-RunID>` dispatches directly to inventory `JobStatus`; legacy 16-byte scope IDs and `v2-` IDs still dispatch to read-only historical readers. There is no shared-directory discovery scan, parent controller, second ledger, scope head or scope stop record in the new route. `scopejob.Start` remains a historical/test execution API; it is not deleted or presented as the new owner.

Config v2 has optional `Enumeration`, `ResourcePolicy`, and `EnumerationRequireGoRoot` fields. Their absence explicitly selects the existing supplied-admission workflow. Their presence freezes canonical metadata policy before effects, under `lsp-trace.inventory-enumeration-resource.v1`. Existing head v4 gains an optional enumeration checkpoint; old serialized heads/configs omit these fields. Segments use `lsp-trace.inventory-scope-segment.v1`; enumeration status uses `lsp-trace.inventory-job-status.v2`, not the old scope report's `closed` meaning. Admission record v2, legacy v2 deadlines and old-v3 refusal are unchanged. No stored bytes are migrated.

`EnumerationConfig` creates metadata-only configuration with no invented model/worker pins. `Create` finishes at `Enumerating/READY`; no metadata has been enumerated. `Enumerate` only accepts that pristine checkpoint. Every batch first claims on the inventory CAS and keeps intermediate checkpoints `CLAIMED`. The cursor, open directory descriptors and traversal offsets are process-local. Losing the process yields `PARTIAL_UNCERTAIN`, never a restart, durable directory offset or refreshed grant. A known funded boundary/limit closes to `EnumerationPartial/PARTIAL`; completed traversal closes to `ReadyForAcquisition/READY`. This latter phase means only metadata enumeration is closed. It never invokes `Describe` or `Seal`, and empty selected scope is not a completed inventory.

All committed scope records are immutable bounded segments under `inventory-scope-<RunID>/segment-<ordinal>.json`. The existing inventory head retains only fixed counters and the final digest; the segment chain carries bounded per-batch records/frontiers. `JobStatus` streams the segments, verifies root coverage and the same shared DFS/frame and classification transition used by legacy readers, and checks only the exact job namespace. A pending orphan is not admitted scope. `CommittedSegmentBytes` counts only committed segment bytes, excluding config, heads and pending/orphan artifacts; it is not total storage telemetry or a physical quota.

### Deliberately bounded funding

This slice **retains the 64 MiB / 64 packet inventory execution profile**. It does not introduce a whole-repository resource profile or enlarge legacy semantic allowances. The scope budget-file logical and packet ceilings are bounded by that policy for new configurations, with at most 30-second operations; the frozen result records the effective caps. Traversal entry/directory/path/depth/filter bounds are retained. All policy-loop work is quoted with the shared `policy-v2` coefficient; the traversal work subcounter is not a second execution grant.

Creation still charges `8*C + 32*(65536+16384) + 32768`, with canonical config at most 32768 bytes and the same bootstrap/final head ceilings. It now additionally checks first-enumeration funding before creating an enumeration job. The first enumeration claim spends the existing fixed scope allowance `4*(256KiB+2MiB)=9MiB` plus the unchanged batch quote `4*(2MiB+4MiB)=24MiB`; each batch spends two packets, and the first claim additionally prepays one closure packet, all from the same cumulative inventory ledger. Each further batch spends 24MiB. The fixed allowance prepays setup/source validation, bounded final readback/namespace checks and bounded status output. There is no discount or refund. Two 128-step batches fit alongside creation; a third does not. Controlled 140/160-selected-file cases complete enumeration; 300-file scope stops paid PARTIAL. **Whole-metadata funding remains deferred**, as does any native-currency acquisition reservation adapter.

Metadata is not source-content identity. Source contents are not read or hashed, and future native acquisition requires paid revalidation. Metadata-only config refuses admission; callers with genuine existing semantic configuration can only reserve after verified enumeration closure and enter existing Collecting. The CLI supplies no such acquisition integration. Multipart/17-file acquisition, full-inventory publication, default census integration and the user's **2 GiB total-retained-storage requirement remain UNMET/deferred**. `MaxAdmittedEvidenceBytes` is still only the narrower post-retention evidence acceptance bound.

Independent parent review is required; passing bounded tests do not constitute acceptance or repository-scale feasibility.
