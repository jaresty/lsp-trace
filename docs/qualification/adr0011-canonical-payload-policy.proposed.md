# ADR 0011 canonical D/R query/result payload — private policy proposal v0

**Status: PROPOSED, UNQUALIFIED; NOT ENABLED.** This is an owner-selected policy proposal for the mandatory canonical query/result payload, not independent maintainer acceptance, a production publisher, an issued method receipt, a terminal ledger, a references query-target identity, an admitted D/R occurrence, qualified Leiden input, or completion of [ADR 0011](../adr/0011-versioned-definition-reference-grouping-evidence.md). Independent maintainers must review and qualify the policy, codec, managed publication and offline verifier before production use. Existing CALLS behavior is unchanged. This proposal selects no new authentication prerequisite: ADR 0011's CALLS-parity `NO_PRODUCER_AUTHENTICATION` ceiling remains.

## Proposed private v0 contract

**Assumption and basis:** ADR 0011 requires a replayable canonical query/result transaction independent of optional raw frames; the private `OwnerPairCanonicalVersion` codec is explicitly unadmitted and does not publish. Therefore the following are *proposed requirements for a future owner-bound implementation*, not properties established by that codec or by the present test-owned publication.

- **Selection and custody.** Default off: without explicit owner configuration for a named versioned policy, positive limits and a pinned private root, write nothing. Only the concrete managed acquisition owner may select the policy/root and derive the private object identity; transport callers and public CLI/MCP inputs must not supply a root, selector, publication capability, or policy override. Require an owner-only 0700 pinned root, 0600 regular single-link objects, and no-replace publication; reject unsafe path replacement or preexisting targets. No public root or selector is created by this proposal.
- **Scope and bounds.** At most 16 explicitly declared exact D/R query occurrences per acquisition; reject undeclared, duplicate or ambiguous occurrence identities rather than inferring a denominator from responses. Accept at most 64 KiB (65,536 bytes) of exact validated JSON params per query, 1 MiB (1,048,576 bytes) of exact successful result JSON per query, and 1,500,000 bytes (below 1.5 MiB) for each complete encoded canonical record including metadata. Check positive bounds before retention and on offline read; never truncate or re-encode an over-bound result into apparent success. These are per-object limits, not a total retained-byte or live-resource budget; total object count/bytes, acquisition duration, live reader wire/messages, CPU, allocation and work must be separately bounded and qualified. Numeric logical-work limits do not establish complete live-wire or CPU coverage.
- **Versioned identity and bytes.** The proposed closed canonical record binds its version and policy ID, selected D/R method, exact query occurrence and validated URI/position/params bytes, managed session/generation/key and collision-safe invocation identity, keyed completed write and accepted matching read observations, capability and provider/adapter metadata *as reported*, source URI and independently characterized revision/document version/digest/encoding custody, explicit result presence versus absence, exact successful result bytes, byte lengths and SHA-256 digests, and result-item ordinals including repeated locations. `null`, `[]`, and absent payload are distinct. Unknown or duplicate fields, inconsistent metadata, stale generation, mismatched response, failure, and malformed or over-bound bytes cannot become a successful record. Caller-asserted source/version information stays caller-asserted; neither a URI nor a digest authenticates source or provider content.
- **Publication state.** A no-replace commit and digest alone are not `VERIFIED`. The existing bound-file primitive can return a receipt with `VerificationStatus=COMMITTED_VERIFICATION_FAILED` after bytes were committed; treat this as committed but *withheld from receipt/admission*, not as no write or a verified success. Only exact post-publication private readback and independent expectation matching may support a bounded `VERIFIED` byte/identity-consistency claim. Directory sync/close statuses and crash-durability limits remain visible privately; `VERIFIED` does not mean producer authentication. Precommit failures produce no successful publication; late failures require private accounting of potentially retained bytes without exposing raw failure text publicly.
- **Independent replay.** Supply expectations independently of the serialized record: policy/version, query occurrence and exact params/URI/position, method, session/generation/key/invocation, expected source and custody fields, capability/provider metadata, result presence and exact result bytes, and each byte length/digest. A bounded reader must check pinned-root custody, exact bytes, closed canonical serialization, selected parameter/result grammar and ordinals, all expected identities, and post-read identity/size stability; self-described fields and a self-hash are insufficient. An expectation copied from the same untrusted record is not independent. A forged, coordinated same-process rewrite of record *and* expectations can still pass: explicitly report `NO_PRODUCER_AUTHENTICATION`, never owner/provider authentication.
- **Withholding and removal.** On server error, timeout, cancellation, partial write/read, unmatched or stale keyed response, malformed/over-bound result, policy mismatch, absent required evidence, publication failure or late verification failure, withhold successful payload/receipt and any new admission. Keep failure accounting separately typed and redacted; public errors/diagnostics must not contain raw params, result/error body, URI, path, selector, or sensitive digest. If privacy withholding or a later reviewed removal makes the mandatory exact result payload unavailable, retain only an explicit withheld/removed disposition as permitted by a separately qualified accounting contract; **no new occurrence admission** may be reconstructed from digest-only metadata or a previously parsed item count. Retain the private canonical payload through explicit qualification review and remove it only on an explicit reviewed decision with accounted success/failure. No automatic 24-hour canonical-payload expiry, guaranteed physical deletion deadline, secure erasure, or backup deletion is claimed.

**Privacy assumption and consequence:** Query URIs and positions can reveal workspace names and code structure; returned locations and digests can disclose sensitive identities even without source bodies. Root access is a privilege boundary only against less-privileged actors, not a sufficiently privileged same-process actor/root custodian. Logs, diagnostic traces, temporary files, hard links, snapshots, backups, and other secondary copies can outlive the reviewed removal; inventory, access control, redaction, recovery and copy-handling need independent qualification. Avoid raw error exposure, including errors surfaced by private publication helpers. The proposal grants no public replay path.

## Separate optional diagnostic

The [private method retention proposal](adr0011-private-method-retention.proposed.md) selects a private default-off **optional exact framed JSON-RPC** request/selected-response 24-hour replay window with lazy cleanup. Its expiry-aware reader and physical cleanup limits govern those frames only. It is neither required to create/replay the canonical query/result payload nor a substitute for its retention, result presence, or byte/identity verifier. Disabling or expiring frames cannot by itself erase a still-required canonical result; conversely a surviving diagnostic frame does not authorize admission when the canonical payload is removed.

## Qualification falsifiers before production publication or receipt

Each row specifies a future executable guard, **not a test claimed to have passed**. A maintainer must independently accept the policy and inspect attributable results; a codec unit test or private candidate readback alone cannot close these gates.

| Guard | Counterexample to inject | Required observation |
| --- | --- | --- |
| Default-off and owner selection | Unconfigured managed D/R success; public/transport-supplied root or selector | No object or publication attempt; no public selection path. |
| Exact boundaries | 65,537-byte params, 1,048,577-byte result, 1,500,001-byte encoded record, seventeenth query, duplicate query, or truncated JSON | No successful retained record, invented smaller denominator, or unredacted error; independent live-resource controls remain measured separately. |
| Owner/keyed consistency | Wrong session/generation/key, changed query URI/position/params, source/version custody, provider metadata, result, ordinal, or keyed response | Offline readback rejects each independent substitution; repeated result locations keep separate ordinals. |
| State and custody | Preexisting target, symlink/root replacement, publication I/O error, or injected failure after no-replace commit | No `VERIFIED` admission on failure; committed bytes are accounted for even when verification fails. |
| Withholding/replay lifecycle | Server error containing secrets; absent result versus `null`/`[]`; reviewed removal with digest still present | Redacted typed failure; distinct result states; no new admission after payload removal. |
| Adversary ceiling | Coordinated same-process replacement of bytes and expectations | Consistency may pass, but no producer/provider authentication is claimed. |

The bounded `internal/adr0011methodresult/owner_pair_canonical.go` v0 codec checks exact independently supplied pair bytes and some identity fields, and `internal/publication/boundfile.go` exposes no-replace and committed-versus-verified states. Neither supplies this complete policy, owner-bound production publication, independent source/version custody, or acceptance evidence. The [decision packet](adr0011-method-receipt-ledger-decision-packet.md) leaves terminal member accounting and references target identity separate. Until those contracts and this policy are independently qualified, no production method receipt, `COMPLETE`/`COMPLETE_EMPTY`, typed D/R occurrence, grouping input or Leiden qualification follows.
